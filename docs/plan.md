- カテゴリ一覧は手動で増減できるようにする。それぞれの品目についてまとめて編集とかもできるように。

# 複数人向け家計簿アプリ — 技術設計・UI/UX構想

このアプリは、単なる家計簿というより、\*\*「複数人の支出・資金・負担・精算を一元管理する、共同編集可能な家計プラットフォーム」\*\*として設計するのがよいと思います。

特に重要なのは、次の4つです。

1. 入力の速さ：手入力では、1品目追加するために必要な操作を限界まで減らす。スマホ・PCそれぞれに適した操作体系を用意する。
2. 精算の正確さ：誰のお金で支払い、最終的に誰が負担すべきかを分離し、入金忘れ・立て替え・貸し借りも正確に扱う。
3. AIによる入力の省力化：レシート、メール、EC注文、カード明細を統合し、ユーザーには確認が必要な部分だけを提示する。
4. 安全な共同編集：複数人が同時に操作しても入力が消えず、後から変更理由と証拠を確認できる。

設計の中心に置きたい考え方は、\*\*「簡単な操作は最短で、複雑な操作は必要になったときだけ表示する」\*\*というものです。

内部構造は高度でも、普段のユーザーには「商品名と金額を入力するだけ」という体験を目指します。

支払った口座の残高変化と、負担先の支出額を混同してはいけません。

### 1.1 共用プールの意味も独立して定義する

共用プールを負担先に指定することと、共用銀行口座から決済することも別です。

例えば、共用プールの支出をAのカードで立て替えることも、共用銀行口座からA個人の服を購入することもあります。

共用プールには、その資金を誰がどの割合で提供するかという資金提供ルールを設定します。初期設定では商品の標準負担割合と同じルールを使い、後から独立して変更できるようにします。

これにより、A・B以外の参加者、複数の共用プール、用途別予算も無理なく扱えます。

### 1.2 標準負担割合の仕様

負担割合は1つの設定だけでは足りません。優先順位を次のようにします。

| 優先順位 | ルール | 例 |
| ---- | ---------- | ------------ |
| 1 | 品目の明示指定 | この服はAが100% |
| 2 | 商品ごとの登録ルール | 牛乳は共用プール100% |
| 3 | カテゴリ別ルール | 日用品はA:B=3:2 |
| 4 | 店舗別ルール | 特定店舗ではAが100% |
| 5 | 家計全体のデフォルト | A:B=3:2 |

ただし、カテゴリ・店舗・商品ルールが競合するときは、明示的な優先度と適用条件を持たせます。

すでに保存された品目には、適用時点の割合を金額とともにスナップショット保存します。 後からルールを変更しても過去の帳簿は書き換わりません。

未確定の入力候補については新しいルールの再適用を提案できますが、入力中の編集内容を勝手に上書きしない設計にします。

### 1.3 精算は予定入金と実入金を区別する

ここが非常に重要です。

例えば、共用口座への予定入金がA:6,000円、B:4,000円で、Bが入金を忘れた場合、共用口座の現在残高だけから不足額を算出することはできません。

予定された入金義務と実際に行われた入金を、別の記録として保持する必要があります。

さらに、共用口座で個人の買い物をした場合は標準負担割合との差分を調整し、個人カードで共用費を支払った場合は立て替えとして精算します。

精算エンジンはこれらを統合し、「次の入金時に誰がいくら払うべきか」「直接送金すべきか」「共用口座に入金することで相殺できるか」を計算します。

会計の正本には複式簿記に相当する不変条件を持つ台帳を採用します。画面上で複式簿記を意識させる必要はありません。

## 2. 最重要：手入力を極限まで簡単にするUI

この2階層をそのままUIに反映するべきです。

### 2.2 スマートフォン：入力中の画面遷移を極力なくす

スマートフォンは縦長でキーボードが画面を占有するため、入力フォームをスクロールしながら大量の項目を埋めさせる設計は避けます。

考えている構成は次の通りです。

画面上部：購入情報

日時、店名、決済元をコンパクトに表示。タップした項目だけ編集できます。

画面中央：品目リスト

通常は商品名、金額、カテゴリ、負担割合の簡潔な一覧。品目をタップすると、その場で展開して編集可能にします。

画面下部：新しい品目の入力

商品名と金額を中心とした入力領域。入力中も直前の品目と合計金額が見えます。

#### 品目追加の操作フロー

1. 商品名を入力

   「ヨー」と入力すると、過去の「ヨーグルト」が候補として現れる。候補を選ばなくてもそのまま入力可能。
2. 金額を入力

   数字入力に移る。カテゴリと負担割合は裏側で補完済み。
3. キーボードの「次へ」で品目確定

   品目を追加し、次の商品名入力に自動的に移る。入力を連続できる。

必要な操作は基本的に 商品名入力 → 金額入力 → 次へ だけです。

ほかにも以下の細かな工夫を入れたいです。

- キーボードが開いている間、入力対象を見失わないよう自動スクロールする。
- 品目確定後は商品名をクリアし、金額や前の入力値が誤って次の品目に残らないようにする。
- 入力候補の表示はキーボード上側に置き、商品の入力欄を押し出さない。
- 通常の確定操作でモーダルを開かない。
- 誤操作したときは即座に元に戻せるUndoを用意する。
- 入力途中に画面を離れても、下書きを自動保存する。
- 日本語IMEの変換確定Enterを、品目追加のEnterと誤認しない。

特に最後の点は、Webアプリで日本語入力を快適にするうえで重要です。`compositionstart` / `compositionend` を考慮し、変換中は確定操作を発火させません。

PCでは逆に、行をまとめて表示するグリッド型が向いています。

また、複数行のテキストやExcelのセル範囲を貼り付けた場合には、品名・価格を解析して複数の品目をまとめて作成する機能も用意します。

自由設定ではAの割合を変えたらBを自動調整するなど、入力欄の操作回数も減らします。

### 2.5 一括編集を非常に使いやすくする

日常的に役立つのは、個々の項目を編集する機能以上に、複数の項目をまとめて変更する機能です。

例えば、10品目中4品目だけAの100%負担にしたい場合。

スマホでは1品目を長押し、あるいは選択モードに入り、複数品目を選んで下部の操作バーから「負担割合」を1回変更します。

PCではチェックボックスに加え、Shiftによる範囲選択にも対応します。

一括編集ではカテゴリ、負担割合、購入先、決済元、日付、タグ、商品名の正規化先などを変更できます。

一括操作の適用時には、対象品目数と変更内容を明示します。操作後のUndoも1操作としてまとまるようにします。

### 2.6 補完・サジェストの理想形

サジェストは、候補を大量に並べることではなく、入力を妨げずに必要な候補を適切な位置に出すことが目標です。

具体的には次のように設計します。

| 対象   | 補完の例                   |
| ---- | ---------------------- |
| 店名   | 時間帯、過去の利用頻度、直近の店舗      |
| 商品名  | 前方一致、略称、購入履歴、店舗ごとの頻度   |
| カテゴリ | 商品マスタ、以前のユーザー修正        |
| 価格   | 過去価格を参考表示。ただし勝手に確定しない  |
| 負担割合 | 商品固有ルール → カテゴリ → 全体ルール |
| 決済元  | 店舗・ユーザー・直近の選択、カード識別子   |
| 日付   | 現在日時、レシート日時、前の購入から継承   |

候補の表示数は通常3〜5件程度で十分です。

さらに、直近の買い物と同じ店舗であれば「同じ店でもう1回入力」、毎回同じ商品を購入するなら「前回の買い物からコピー」を用意します。ただし、過去の価格を自動的に正しいものとみなさないことが重要です。

## 3. AI入力のUIも「認識結果のフォーム表示」では不十分

AI入力では、認識処理そのものよりも、人間がどれだけ少ない操作で確認・訂正できるかが重要です。

理想の操作は次のようなものです。

1. スマホでレシートを撮影する。複数枚の撮影や画像の追加も同じ画面で可能。
2. AIが品目、価格、税、値引き、店名、日時、決済元、カテゴリ、負担割合を提案する。
3. 画面には認識した品目が表示され、問題がありそうなところだけ目立つ。
4. 利用者は間違った部分だけを直し、合計額を確認して確定する。
5. 確定後もレシート画像やメールとの対応関係を維持する。

確認画面の概念図。実際には元画像を表示し、対応領域をスクロール・拡大・ハイライトします。

PCでは、品目にマウスを乗せると画像上の該当部分が強調され、逆に画像をクリックすると対応する入力項目に移動します。

スマホでは、品目をタップすると、対応部分の画像がその品目のすぐ上に表示される方式を基本にします。画像全体の確認にも1操作で切り替えられます。

レシートを見ながら訂正するために、別画面を往復する必要がない設計です。

### 3.2 認識の信頼性をUIに反映する

AIの推定値を、すべて確定済みのように表示するのは避けます。

特に重要なのは、値の由来です。

- 原本から直接取得：レシートに記載された金額・商品名
- 別ソースで照合済み：レシート合計とカード明細の一致
- 履歴から推定：省略商品名の補完、カテゴリ、負担割合
- 未確認：読めなかった文字、整合しない金額、重複の疑い

ただし、すべての品目に色付きの警告を出すのではなく、通常は静かな表示にします。異常がある行だけ視覚的に区別し、上部に「確認が必要な項目が2件」などの要約を表示します。

利用者が直した値については、その入力を優先し、後続のAI処理が黙って再変更しないようにします。

### 3.3 修正作業も学習に利用する

例えば、レシートに「ヨーグルトPB 400」と書かれており、ユーザーが「プレーンヨーグルト400g」に修正したとします。

この修正から、単なる文字列置換だけでなく、店舗、商品ID、正規化した名称、カテゴリ、負担ルールの関係を学習します。

次回は同じ商品の正規化候補が自動的に適用され、確信が低い場合だけ候補として提示されます。

個人開発でも、こうした修正履歴を蓄積すれば、使うほど操作量が減っていくアプリになります。

## 4. 精算エンジンの具体的な設計

精算については、内部的に2種類の台帳を持たせます。

- 資金・債権債務台帳：実際の支払い、入金、立て替え、貸付、返済など。
- 負担・入金義務台帳：各品目の最終負担、定期入金予定、未履行額など。

そして「負担割合」と「共用口座への定期入金割合」が同じ初期設定であっても、計算上は独立した情報として扱います。

### 4.1 次回入金額の算出

例えば、以下のような状況を考えます。

| | A | B |
| --------- | ------ | ------ |
| 先月の入金予定 | ¥6,000 | ¥4,000 |
| 先月の実入金 | ¥6,000 | ¥0 |
| 未入金 | ¥0 | ¥4,000 |
| 今月の通常入金予定 | ¥6,000 | ¥4,000 |
| 次回必要入金額 | ¥6,000 | ¥8,000 |

この例では、入金忘れだけを考慮しています。

実際の精算では、ここに個人負担の差分、立て替え、先払いなどを加味します。

基本形は次のようになります。

\\[ \begin{aligned} \text{次回入金額}\_i ={}&\text{通常入金予定}\_i\\\ &+\text{過去の未入金}\_i\\\ &+\text{追加負担調整}\_i\\\ &-\text{立替・先払い控除}\_i \end{aligned} \\]

ただし、実際の実装ではこの式を独立した計算処理として持つよりも、台帳上の債権債務から算出する方式にします。

特に重要なのは、共用口座からの支出について、どの金額が通常の積立で賄われる想定だったかです。

例えば、共用口座で1,000円のA専用商品を購入し、通常の積立で賄われる共用支出の基準割合が60:40だった場合、通常配分との差はAが+400円、Bが−400円になります。一方、その商品が通常の積立予算の対象外なら、Aが追加で1,000円を補填する方式も考えられます。

どちらが適切かは資金運用ルールによって違います。そこで以下の2つを明示的に設定できるようにします。

| 精算ポリシー | 動作 |
| -------- | ----------------- |
| 負担割合の平準化 | 標準割合と実際の負担割合の差を調整 |
| 予算外支出の補填 | 共用資金を個人利用した金額を補填 |

これを区別しないと、家計簿上は正しそうに見えるのに、実際の口座残高や誰のお金なのかが一致しなくなります。

精算画面は、計算式を見せるのではなく、まず行動を示します。

実際には、各金額の内訳をクリックすると、根拠になった入金予定、実入金、品目、立て替え履歴へ移動できるようにします。

負の必要入金額が出た場合も、単純に0円に丸めて消してはいけません。過払い残高として繰り越す、共用口座から返金する、ほかの人への送金と相殺する、といった方法を提案します。

### 4.3 立て替え・貸付・贈与も別々に扱う

特に次の違いは重要です。

| 取引 | 支出集計 | 精算への影響 |
| ------------ | ---------- | ------- |
| AがBの服を立替購入 | Bの衣服費 | BがAに返す |
| AがBに5,000円貸付 | 支出には含めない | Bに返済義務 |
| AがBに5,000円贈与 | 家計消費には含めない | 返済義務なし |
| Aが共用口座に入金 | 支出には含めない | 入金義務の履行 |
| AがBに借金を返済 | 支出には含めない | 債務を減額 |

また、共用口座を介して返済するか、個人間で直接返済するかも選択できるようにします。

### 4.4 締め処理と修正

締め済みの帳簿には、確定した品目別金額、負担割合、入金義務、精算結果、ルールのバージョンを保持します。

締め後に間違いが発覚した場合は、通常の編集で過去を書き換えるのではなく、訂正仕訳・調整取引を追加します。

必要に応じて元の取引を参照し、購買日ベースの分析は訂正後の金額に、精算は次回の調整に反映するという運用ができます。

### 5.2 レシート認識は単一のAIモデルに全面依存しない

私なら、次のハイブリッド構成を採用します。

| 処理 | 推奨方式 |
| ---------- | ---------------- |
| 画像補正 | ローカル画像処理 |
| 文字・位置の抽出 | OCR＋必要に応じてGemini |
| レシート全体の理解 | Geminiの画像理解 |
| 商品名・店舗名補完 | 過去データとの照合＋LLM |
| 税額・合計・差額検証 | Goによる確定的な計算 |
| 重複検出 | ハッシュ＋確率的照合 |
| 負担割合決定 | ルールエンジン＋過去の修正 |
| 最終保存 | 人間の承認とサーバー側検証 |

例えばOCRが「ﾖｰｸﾞﾙﾄP 400」と認識した場合、LLMは履歴を参照して正式名を補完できます。

ただし、レシートに存在しない商品を推測して勝手に追加してはいけません。

金額も、モデルの出力をそのまま保存せず、商品金額・値引き・税・合計金額の関係を検証します。

日本のレシートでは、8%・10%の税率混在、内税・外税、明細単位と会計単位の端数処理、ポイント使用、クーポン、返品なども扱う必要があります。

端数計算は実際のレシートの金額に合わせ、割り切れない1円は安定したルールで配分します。

### 5.4 複数のソースを照合する方法

例えば、Amazonで次の商品を買った場合。

- 注文メール：商品2点、合計4,980円
- カード明細：Amazon 4,980円
- Amazon注文画面：商品名、個別価格、注文番号
- 銀行明細：後日カード引落し

これらを4件の支出として登録してはいけません。

内部で各ソースをObservation（観測情報）として保存し、同一の経済的な取引を指しているか照合します。

照合に使う情報は、注文番号、取引ID、金額、日時、店舗、カード末尾番号、品目の組み合わせなどです。

照合の状態

| 一致が確定 | 同じ取引に証拠を追加 |
| --------- | ---------------- |
| 一致の可能性が高い | 統合候補として提示 |
| 金額や件数が矛盾 | 未照合として残し、確認可能にする |
| 別取引 | 新しい取引候補を作成 |

Amazonでは特に、1注文が複数発送・複数決済に分かれることがあります。注文とカード決済を1対1で紐付けるのではなく、多対多の関連を許容します。

また、カード利用記録とカード会社による銀行引落しも別の資金移動であり、後者を新しい購入支出として集計しないことが重要です。

## 6. 商品名・カテゴリの正規化

商品名は、ユーザーが入力した名称と、内部で管理する正規化商品を分けて保持します。

例えば、次のようになります。

```
正規化商品
  プレーンヨーグルト 400g
    ├─ ヨーグルト
    ├─ ヨーグルトPB400
    ├─ PBヨーグルト 400
    └─ ﾖｰｸﾞﾙﾄP 400
```

ただし、「ヨーグルト」という一般名を特定の商品に自動統合してしまうのは危険なので、確信できる場合だけ同じ商品とします。

商品管理には、少なくとも次の階層を用意します。

`Product Concept → Product Variant → Merchant-specific Alias`

例えば「牛乳」という一般商品概念の下に、メーカー・容量の異なる商品を持たせ、店舗固有の略称を結び付けます。

商品名、カテゴリ、店舗は、PostgreSQLの全文検索や`pg_trgm`等を使ったあいまい検索でまず十分です。日本語の部分一致を重視する場合は、文字n-gramや適切な日本語トークナイザも検討します。

Qdrantは意味検索で明確なメリットが出る場合に導入します。すべての文字列にEmbeddingを作る必要はありません。

さらに、ユーザーが品名を修正した場合の学習対象は分離します。

- この取引だけ変更
- 同じ商品の正規化名を変更
- 同じ店舗の表記ゆれとして登録
- 今後のカテゴリや負担割合のルールとして保存

推定が不確かなときだけ、邪魔にならない小さな提案を表示します。

### 7.1 Next.jsではなくTanStack Startを選ぶ理由

今回のアプリは、SEOが重要な公開Webサイトではありません。

必要なのは、柔軟なルーティング、認証、フォームの状態管理、軽快なクライアント動作、十分なSSR、共同編集です。

TanStack Startはこれらに適しており、Next.js特有のServer ComponentsやServer Actionsを中心に設計する必然性は小さいと考えます。

Go APIを独立させるので、フロントのフレームワークを交換しやすい点もメリットです。

画面ごとにファイルベースのルートとURLを割り当てます。画面の選択にクエリパラメーターを使わず、ブラウザーの再読み込み、戻る、進むでも同じ画面を開けるようにします。クエリパラメーターは帳簿の絞り込みなど、URLで共有・復元する画面状態に限って使います。

未保存の入力があるときは、アプリ内の画面遷移とブラウザー離脱の両方で確認を行います。購入入力は下書きを保存し、再読み込み後に復元します。スマートフォンでドロワーを開いている間は、背景ページを固定してoverscrollによる意図しない再読み込みを防ぎます。

### 7.2 GoかフルスタックTSか

両方で実現できますが、今回の要件ではGoを選びます。

理由は、会計処理をUIから完全に切り離し、金額・負担配分・精算・締めの不変条件を単一のサーバー側ドメインとして扱いたいためです。

これはTypeScriptでも可能ですが、Go + PostgreSQLのトランザクション処理で実装する構成が、今回の既存インフラとの親和性も高いでしょう。

GraphQLは、購入単位で必要な品目・負担情報をまとめて取得できること、型生成とフロントの連携がしやすいことから適しています。

フロントのAPIキャッシュにはRelayを採用できます。すでにリアクティブなクライアントキャッシュを持てるので、別の同期データベースまで重ねる必要はありません。

### 7.3 同時編集の実現方法

複数人が編集する場合、単にWebSocketで更新通知を流すだけでは不十分です。

推奨する方式は以下の通りです。

1. 各購入・品目にリビジョン番号を付ける。
2. 編集を楽観的に即時反映する。
3. 更新要求には基準リビジョンと変更したフィールドを含める。
4. サーバーでは同一トランザクション内で検証・確定する。
5. 確定した変更をSubscriptionで他の利用者へ配信する。
6. 接続が切れた場合は変更カーソルによって再同期する。

例えば、Aが品名を変更中にBが同じ品目のカテゴリを変更した場合は、フィールド単位で矛盾なく統合できます。

一方、AとBが同じ商品の負担割合を同時に変更した場合は、勝手に後勝ちで上書きせず、競合を明示して選択できるようにします。

特に金額や負担配分は複数フィールドで1つの整合性条件を構成するため、変更単位をまとめて扱います。

YjsのようなCRDTは自由なテキストの共同編集に向いていますが、金融台帳の金額や負担割合を自由にマージする用途には適しません。Yjs自体は共同編集・同期を目的としたCRDTです。

[image](https://www.google.com/s2/favicons?domain=https://docs.yjs.dev\&sz=32)

Yjs Docs

+1

また、オフライン下書きをIndexedDBに保持し、再接続時に冪等キーで再送します。未送信の入力、競合、同期済みは明確に区別します。

なお、将来的な代替案として、ElectricSQL + TanStack DBによるPostgreSQLのリアルタイム同期も技術的に魅力があります。現在のTanStack DBにはElectric CollectionやOptimistic Updateへの対応がありますが、これを使う場合も会計更新はサーバー側で確定させる必要があります。

| 入金予定    | `funding_schedules`, `funding_obligations`             |
| 精算      | `settlement_runs`, `settlement_adjustments`            |

重要な設計ポイントを挙げます。

金額は整数の最小通貨単位で保持し、Floatを使いません。円なら1円単位です。負担割合は有理数または精度が決まったDecimalで保持し、最終配賦金額は整数として確定させます。

`purchases`は1回の購入イベントを表し、`purchase_items`が実際の品目を管理します。すべての品目は`purchase_id`で親に紐付きます。

`item_allocations`には、品目ごとの各プールの負担額、適用割合、適用ルールのバージョンを保持します。

`source_documents`は原本とハッシュ、`observations`はその原本から認識した事実を保持します。原本そのものはSeaweedFSに保存します。

`journal_entries`は確定済みの会計仕訳を保持し、変更時には訂正仕訳を追加します。

トランザクションの冪等性、負担額の合計一致、仕訳の貸借一致、精算の二重適用防止はDB制約とサーバー側処理の両方で保証します。

また、各家庭を独立したテナントとして扱い、GraphQLの全操作でサーバー側の所属・権限チェックを行います。

## 1. OCRをメインの前処理にするべきではない

指摘のとおりです。

```
ヨーグルト      150 *
シャンプー      500

8%対象額       150
10%対象額      700

合計            918
```

この例では、印字された`*`が軽減税率の対象を示している可能性があります。

OCRがこの記号を落としたり、金額を別の行に結びつけたりすると、後段のLLMが適切に理解できなくなります。

さらに、税額の表示が下部にまとまっていたり、割引が特定の商品に紐付いていたりする場合、テキストの単純な並びだけでは意味を正しく解釈できません。

### ローカルOCRの役割

ここでOCRを使用する目的は、LLMへの情報圧縮ではありません。

- LLMが「198円」と読んだ箇所を、OCRでは「196円」と読んだ場合に不一致を検出する。
- 画像内のテキスト位置を、レシートと品目を結ぶUIに利用する。
- 商品名や店舗名の全文検索用インデックスを作る。
- LLMが読み飛ばした行を検出する。
- 不鮮明な箇所だけを高解像度で再解析する。

OCRの出力は、LLMの出力と同じく観測結果です。どちらかを無条件に正解とはみなしません。

また、OCRが文字を認識できなかったことを理由に、LLMによる直接画像認識を諦めることもありません。

### 画像の前処理も慎重に行う

写真の回転、遠近補正、明るさの調整、余白のトリミングは有用ですが、補正によって細い文字が消えることがあります。

そのため、必ず原本画像を保存し、解析用の補正画像も別に管理します。

長いレシートでは、全体画像を提示したうえで高解像度の重複領域付きクロップを併用します。画像全体を小さく縮めてしまうのは避けます。

## 2. 税の計算は「解釈」と「計算」を分離する

ここも前回の設計を修正するべきです。

税の計算式は決定的でも、その式に入力する税率、税抜・税込区分、値引きの適用先、端数処理方法が不明な場合があります。

例えば、同じ「100円」という印字でも、次の可能性があります。

- 税抜100円、8%対象
- 税抜100円、10%対象
- 税込100円、8%対象
- 税込100円、10%対象
- 非課税・不課税
- 商品価格ではなく割引後価格

しかも1つのレシート内に複数の税区分が存在することもあります。

日本の適格請求書制度では、消費税額の端数処理は原則として1枚の請求書につき税率ごとに1回で、切上げ・切捨て・四捨五入のいずれも認められています。

### 2.1 税務情報を含めた構造化データ

各品目に次のような情報を持たせます。

税率は日付に依存するマスタで管理し、8%・10%をコードに固定しないようにします。

### 2.2 レシート全体から計算方式を推定する

商品ごとに独立して税を決定するのではなく、レシート全体の制約を使って税の扱いを解釈します。

例えば、

- 商品A：100円、軽減税率
- 商品B：200円、標準税率
- 合計：328円

と書いてあれば、両方税抜で8円＋20円の税を加えている、という解釈が有力です。

しかし別のレシートで合計300円なら、両方税込である可能性が高くなります。

実際には以下も考慮します。

| 情報 | 推論に利用する内容 |
| ------------ | ----------------- |
| 商品名 | 軽減税率対象かの参考 |
| `※`、`*`などの記号 | 店舗固有の税率表記 |
| 税率別対象額 | 税率グループの金額制約 |
| 消費税額 | 税額・丸め方式の制約 |
| 値引き行 | 特定品目・税率群・会計全体への適用 |
| 合計額 | 最終的な整合性 |
| 過去の同店舗レシート | 税表示・端数処理パターン |
| 購入日 | その時点の税制・税率 |

ここは、LLMに計算させるのではなく、次のような処理にします。

1. LLMが画像から税に関する観測事実と解釈候補を出す。
2. Goの検証エンジンが候補ごとの金額を計算する。
3. レシートの税率別小計・総額・支払総額と照合する。
4. 複数候補が成立する場合は、履歴や原本の表示から絞り込む。
5. 一意に確定できなければ、推定として保持する。

複数の方式が同じ合計額になることもあるため、合計が一致しただけで税解釈を確定扱いにはしません。

### 2.3 商品別の税込負担額をどう確定するか

例えば、税抜商品を複数購入し、消費税額がレシート全体でまとめて計算されている場合、1商品ごとの「正確な税込価格」はもともと印字されていないことがあります。

それでも家計簿では商品ごとの税込負担額が必要です。

そこで、合計金額が必ず一致するように、税率グループ内で税額を各品目に配賦します。

基本は税抜金額に比例して配賦し、1円未満の端数は最大剰余法などで処理します。

ただし、これは家計簿上の配賦額であって、レシートに印字された商品別税込価格と同一とは限りません。

内部では印字額、推定税率、配賦後の金額を別々に保存し、必要であれば再計算できるようにします。

また、値引き、ポイント払い、送料、返金、商品券などはそれぞれ性質が違います。支払額が減ったからといって、必ずしも商品価格の値引きではありません。

この違いもLLMで認識し、計算エンジンで整合性を確認します。

## 3. 過去の膨大な取引をどう推論に使うか

ここでは、単純に過去100件や1,000件をプロンプトに入れる方法は採用しません。

必要なのは、入力されたレシートに関係する情報だけを選び、十分にコンパクトな形でLLMに渡すことです。

また、過去の情報を渡しすぎると、モデルが新しい画像より過去の情報を優先してしまう問題もあります。

そのため、「画像の事実を読むこと」と「履歴を参考に補完すること」を論理的に分けます。

### 3.1 過去の情報を4階層で管理する

| データ | 内容 | 推論での役割 |
| --------- | ------------------ | -------- |
| 店舗プロファイル | 店名、税表示、レシート構造、決済方法 | レシートの解釈 |
| 商品マスタ | 正規化名、別名、JAN、カテゴリ | 商品の識別・補完 |
| 取引履歴 | 購入商品、金額、時期、店舗 | 候補のランキング |
| ユーザーの修正履歴 | AIの誤り、人間による訂正 | 誤認識の再発防止 |

ここで非常に重要なのは、モデルに渡す情報と、ローカルで確定できる情報を区別することです。

例えば、「この商品は食料品カテゴリで、A:B=3:2」という設定がDBに存在するなら、LLMに負担割合を再推論させる必要はありません。

Goで確定的に適用できます。

LLMを使うのは、レシート上の商品と商品マスタを結びつけるときなど、曖昧性がある箇所に限定します。

### 3.2 検索・補完の具体的なフロー

レシート画像から次のように読み取れたとします。

```
店舗：スーパー〇〇
商品名：PBヨーグルト400
金額：158円
```

この情報を使って、まずPostgreSQLから関連する候補を検索します。

```
1. スーパー〇〇の店舗プロファイル
2. この店舗でよく購入する商品
3. "PBヨーグルト400" の完全一致・別名一致
4. 文字列が類似する正規化商品
5. 金額・容量・購入頻度が近い候補
6. 過去に人間が修正した類似レシート
```

そして、LLMに次のような限定的な情報だけを渡します。

```
{
  "observed": {
    "merchant": "スーパー〇〇",
    "raw_name": "PBヨーグルト400",
    "amount": 158
  },
  "candidates": [
    {
      "id": "product-101",
      "canonical_name": "PBプレーンヨーグルト 400g",
      "aliases": ["PBヨーグルト400"],
      "prior_price_range": [138, 178],
      "merchant_match": true
    },
    {
      "id": "product-202",
      "canonical_name": "飲むヨーグルト 400ml",
      "aliases": ["ヨーグルト400"],
      "prior_price_range": [168, 238],
      "merchant_match": false
    }
  ]
}
```

モデルには、候補を選ぶか、一致なしと判定するかを求めます。

このようにすれば、履歴が10万件あっても数件〜十数件程度の情報で十分に推論できます。

### 3.3 履歴検索には何を使うべきか

最初からQdrantによるベクトル検索を全面採用する必要はありません。

今回のような商品名検索は、意味的な近さだけでなく、型番、内容量、メーカー、数字の一致が非常に重要です。

「牛乳1L」と「牛乳500ml」は意味的には似ていますが、正規化商品としては別にしたい場合があります。

そこで、次の順番がよいです。

1. 完全一致・店舗固有の別名一致
2. JAN・ASINなどの商品識別子の一致
3. PostgreSQLの文字列類似検索
4. 店舗・価格・購入頻度によるランキング
5. 必要な場合だけEmbeddingによる候補追加
6. 残る曖昧さをLLMで判断

Embeddingはローカルの小型モデルで生成できます。Qdrantを使う場合も、Embedding検索だけで確定するのではなく、型番・容量・ブランドの一致を検証します。

### 3.4 学習データは明示的な訂正を重視する

例えば、AIが以下のような誤りを出した場合。

- 認識：「牛乳」
- 実際：「豆乳」
- ユーザー修正：「調製豆乳 1L」

この訂正は強い教師信号です。

ただし、これを機械的に文字列置換ルールへ変換すると、別の店舗の別商品に誤って適用してしまいます。

したがって、訂正を次のように扱います。

```
Correction
 ├─ original observation
 ├─ corrected value
 ├─ merchant
 ├─ source region
 ├─ product match
 ├─ model version
 └─ user-confirmed rule
```

これを再検索時の特徴量とし、十分な根拠がある場合のみ自動適用します。

また、過去のAIによる推定結果を、ユーザーが確認していないのに正解データとして再利用し続けるのは避けます。誤りが自己増殖するためです。

### 3.5 毎回LLMに履歴を全部渡さなくてもよい

コスト面・精度面では、次の使い分けがよいです。

第一段階：原本画像の抽出

画像をそのままLLMに渡し、印字されている文字・金額・税表示・領域を中心に抽出します。履歴の影響で文字を勝手に補完させないことが目的です。

第二段階：ローカルでの正規化

商品・カテゴリ・店舗・カード識別子の候補をDB検索やルールで決定します。明確なものにはLLMを使いません。

第三段階：曖昧な項目だけ推論

候補が複数存在する場合に限り、関連する過去の情報を添えてLLMに判断させます。

この設計なら、過去の履歴が増えるほど推論コストが増えるという構造になりません。

### 4.4 既存のKubernetesクラスタでどう動かすか

手元のGTX 1070 8GBやCPUノードを利用するなら、まずPP-OCRv6のCPU推論を基本とします。

モデルがVRAMに収まっても、推論バックエンドが対応していない可能性があります。

また、常時GPUを占有しないようにします。CPU OCRは通常のWorkerで処理し、GPUを使用するモデルだけ必要時に起動させる方式がよいでしょう。

### 5.3 ローカルAIとのコスト比較

ここが興味深いところです。

クラウドAIの料金が月数百円であれば、すでに存在するGPUを使用したとしても、必ずしもローカル推論が安いとは限りません。

例えば、追加で100Wを使用するGPU処理があると仮定します。電気料金を30円/kWhとすると、

| 稼働状況 | 追加電気代 |
| --------------- | ------- |
| 100Wで月10時間推論 | 約30円 |
| 100Wで月50時間推論 | 約150円 |
| 100Wで24時間×30日稼働 | 約2,160円 |

これはGPUの実測値ではなく、比較用の100W一定という仮定です。待機電力、ホスト側の消費電力、冷却、GPU以外のワークロードは含んでいません。

クラウドのGemini 3.8 Flashなら、通常のレシートを1枚解析するためのAPI料金は仮定上わずか約2.5円です。

さらに、GPUモデルをロードするためにVRAMを占有したり、GPU対応のコンテナを維持したり、ローカルVLMの推論性能を最適化したりする運用コストも考慮する必要があります。

一方、PP-OCRv6のような小型モデルをCPUで実行する場合は、クラスタ内の既存リソースを効率よく活用できる可能性が高いです。

したがって、推奨方針は次の通りです。

ローカル推論

- 小型OCR、画像補正、類似画像検出、Embedding、検索・正規化を担当。
- CPUで十分な処理を優先し、必要な場合だけGPUを使用。

クラウド推論

- レシート全体の意味理解、税表示の解釈、難しい商品名・支払情報の抽出を担当。
- 確信が持てない部分だけ再解析。

これが、現時点で品質と運用コストのバランスが最もよい構成だと考えます。

なお、Gemini 3.8 Flashの料金が予定どおり2027年に倍増しても、今回の標準利用量の試算では月400円強程度です。ただし他モデルの価格や利用状況が同じという仮定です。

### コンポーネントの分離

Goのバックエンドを前提とするなら、次のような内部構成を推奨します。

| コンポーネント | 担当 |
| ------------------------ | ------------------ |
| `document-ingestion` | 画像・PDF・メール・注文情報の受付 |
| `document-preprocessing` | 画像補正・ハッシュ・クロップ |
| `vision-extractor` | Geminiを使った直接画像解析 |
| `ocr-extractor` | ローカルOCRによる独立解析 |
| `evidence-store` | 画像と抽出結果の紐付け |
| `receipt-interpreter` | 税、値引き、支払方法の解釈 |
| `transaction-reconciler` | 複数ソースの照合・重複防止 |
| `product-resolver` | 商品検索・正規化・カテゴリ推定 |
| `verification-engine` | 金額整合性、矛盾、推定の検証 |
| `model-router` | モデル選択・再試行・コスト制御 |
| `correction-learner` | 人間による訂正の蓄積 |

実際のKubernetes上では、これらを全部別Deploymentにする必要はありません。

論理的なコンポーネントとして分離し、GoのWorker、Pythonのローカル推論サービス、GoのGraphQL APIなどにまとめられます。

### モデルルーティングは動的にする

モデルを単純に固定するのではなく、検証結果と過去の実績を使って動的に選択します。

例えば、ある店舗のレシートが毎回きれいに認識できて、安価なモデルでも正答率が十分なら、次回から安いモデルを利用する余地があります。

逆に、その店舗のレシートが難しいことが分かっているなら、最初から高品質なモデルを使用します。

ただし、毎回のレシートが同じ形式であるとは限りません。入力画像の品質や明細数、税率の混在、値引きの複雑さなども条件に含めます。

また、モデルの判断はルールだけで確定させず、実際の検証結果を参照して更新します。

## 7. 精度を評価する仕組みも最初から組み込む

今回のアプリでは、AIモデルの名称よりも、実際のレシートに対する精度が重要です。

そのため、モデルを導入する前に評価基盤を用意するべきです。

例えば、100〜300枚ほどの日本語レシートを集め、以下のような正解データを作成します。

- 店名・日時
- 品目数
- 品目名と原文
- 商品ごとの印字額
- 税抜・税込区分
- 税率
- 商品ごとの最終負担額
- 値引き・ポイント・支払方法
- レシート上の対応領域

ここで比較するのは、単なる文字認識の正答率だけではありません。

| 指標 | 意味 |
| ------------------ | ------------------------ |
| 品目検出Recall | 買った品目を何件見落としたか |
| 金額完全一致率 | 品目金額が1円単位で一致した割合 |
| 税額整合率 | 税率別小計・合計の一致 |
| 商品正規化精度 | 正しい商品マスタに紐付けられた割合 |
| Evidence Precision | 認識した品目が正しい画像領域に結びついている割合 |
| 自動確定可能率 | 人間による修正が不要だった割合 |
| 平均修正操作数 | 1レシートを確定するのに必要な操作数 |
| 1件当たりAPIコスト | 精度と費用のバランス |

ここで特に重要なのは、\*\*「1文字でも間違ったか」よりも「ユーザーが何回修正する必要があったか」\*\*です。

1枚のレシートに20品目があり、そのうち1品目の商品名の一部が間違っているだけなら、修正は簡単です。

一方、1品目を丸ごと読み飛ばしたり、値引きの関係を間違えたりすると、ユーザーがレシート全体を見直す必要があります。

したがって、最適なモデルを選ぶ評価関数には、精度・料金だけでなく人間の修正時間も含めます。

こうすれば、たとえ高性能モデルのAPI料金が1枚当たり数円高くても、修正を減らせるなら積極的に採用できます。

## 結論：採用したい構成

AI処理の採用方針

| 主解析 | Gemini 3.8 Flashで画像を直接理解 |
| ------- | ------------------------------ |
| 独立した読取 | ローカルPP-OCRv6を補助的に使用 |
| 税の解釈 | LLMによる仮説生成＋Goによる制約検証 |
| 過去の履歴 | PostgreSQLで関連候補を検索、必要な情報だけLLMへ |
| 難しいレシート | 高解像度クロップ、必要ならGemini Pro |
| メール・EC | 構造化パーサー＋Flash-Lite |
| 精度改善 | 訂正履歴・評価データ・店舗別ルーティング |

前回の設計との最も大きな違いは、OCRを画像情報の代替にしないこと、税の解釈に曖昧性があることを正式にデータモデルへ組み込むこと、履歴の活用を検索ベースにして推論コストと誤推論を抑えることです。

さらに、実際のAPI料金が月数百円程度であることを考えると、クラウドの高品質なモデルを基本にして、ローカルAIは得意な処理に集中させる構成が合理的です。

これは機能を削減するための設計ではありません。最初から複雑な税計算、長いレシート、複数証拠、訂正履歴、モデル変更、ローカル推論への切替をすべてサポートできるようにしておきます。

そしてAIが誤った推定をした場合でも、何を画像から読み取り、何を過去の履歴から推測し、何を計算によって導いたのかを常に追跡できる状態にすることが、信頼できる家計簿を作るために最も重要だと思います。
