# 原本オブジェクトの保存暗号化

新規アップロードはS3の`AES256`サーバー側暗号化を要求し、`household/originals/sse-v1/<sha256>`へ`If-None-Match: *`付きで作成します。`PutObject`成功応答に`AES256`がない場合も保存失敗として扱います。同じキーの既存データは暗号化ヘッダー、SHA-256、サイズ、再取得した内容を照合します。SeaweedFSはSSE-S3用KEKが設定されていないと暗号化要求を拒否します。アプリケーションは暗号化に失敗したとき平文保存へ切り替えません。

`sse-v1`の読み取りでは、S3の暗号化応答ヘッダーと原本データのSHA-256を検証します。以前の`household/originals/<sha256>`は既存原本として読み取りますが、暗号化済みとは扱いません。新しい暗号化設定は既存オブジェクトの内容やキーを変更しません。条件付き作成はアプリケーション経由の上書きを防ぎますが、削除権限による削除までは防ぎません。infraはHorseのS3 principalに原本prefixの削除を許可しない設定を確認し、設定が確認できるまでは不変性を保証済みと扱いません。

SeaweedFSの全S3ゲートウェイは同じKEKを使う必要があります。KEKはinfraがOnePassword itemとして管理し、TerraformとESOからSecretとして渡します。OnePassword itemの独立バックアップ、アクセス権、復旧責任はinfraの運用手順で管理します。SeaweedFSのデータを別クラスタへ復元する場合は、バックアップした同じKEKを全S3ゲートウェイへ復元してからデータを読みます。復旧確認では新規テストオブジェクトの`HeadObject`で`AES256`を確認し、保存系の再起動または切替後に`GetObject`で読み戻した内容のSHA-256を照合します。鍵を復元できない場合、SSE-S3オブジェクトを読み取れません。鍵の値や原本データをログ、Terraform出力、バックアップ対象の平文設定に含めないでください。

既存原本を暗号化する移行が必要になった場合は、元のキーを上書きしません。移行ジョブは世帯ごとに原本を読み、DBに記録されたSHA-256を検証し、`sse-v1`キーへ条件付きで保存して新しい保存先を再読込・照合した後、Bobの生成モデルと単一DBトランザクションを使って参照キーを更新します。元の平文オブジェクトは、バックアップと保持期間を確認する別の承認済み削除処理まで残します。このリポジトリには既存原本の一括移行ジョブはありません。

料金・精度の評価用データには原本画像を含めず、実際の利用者データを公開データセットへ追加しません。
