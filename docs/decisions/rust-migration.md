# Rust移行

## 状態

Rust移行は本番へ反映済み。CLIを除くGoの実行コードをRustへ移し、Go Backendを削除した。空のPostgreSQLへAtlas migrationを適用してDiesel schemaを生成し、本番DBを再作成した。2026年10月17日時点でRust API・Worker・Web・OCRはKubernetes上でReadyになり、`horse.walnuts.dev/healthz`はHTTP 200を返した。

## 決定

CLIを除くBackendの実行コードをGoからRustへ移行する。Rust API、Worker、GraphQL契約、デプロイ定義をRust実装へ揃え、既存Go実装とのGraphQL互換性を移行条件にしない。Rust実装への切り替えで本番DBをリセットし、新しいschemaを作成する。

PostgreSQLのスキーマとmigrationの正本にはAtlasを使う。RustからのDBアクセスにはDiesel 2.3と`diesel-async` 0.9.2を使い、Atlas適用後のスキーマから生成した型定義を基に、型付きQuery DSLで実装する。Dieselのmigration機能と`sql_query`による生SQLは使わない。DSLで表現できない要件はクエリやスキーマを見直して解決する。

業務処理はDMMFに沿って、入力と現在状態から結果・イベント・失敗を値として返すpure Decisionと、DBや外部サービスのI/Oを行う実行境界に分ける。DecisionはI/O、GraphQL、永続化型に依存させない。実行境界が必要な読み込みを行い、Decisionを呼び出し、その結果に基づいて書き込みとイベント配送を行う。

Workspaceは`apps/`にComposition Root、`contexts/<bounded-context>/{domain,application,postgres}`に業務ごとの実装、`adapters/`にGraphQL・HTTP・Identity・AI・Workerの接続、`platform/postgres-common`に接続Poolと生成済みDiesel Schemaを配置する。複数Contextを横断する読み取りは`contexts/cross-context/postgres`に置く。Householdは家計のDefaultとメンバー・招待設定、PolicyはPoolと負担・拠出ルール、Bookkeepingは口座・仕訳・購入・精算Snapshotを所有する。更新処理とその業務判断は状態を所有するContextに置き、別Contextの更新が必要な場合はApplication契約を通じて同一transaction内で実行する。

Application Workflowは業務操作のLoad・Decision・Persistの順序を所有し、小さな操作契約を通じてPostgreSQL AdapterへI/Oを要求する。PostgreSQL AdapterがDieselのtransactionとロックを維持し、Workflow全体を原子的に実行する。GraphQL ResolverはDTOを認証済みActor付きCommandへ変換し、Application Workflowを呼び出す。

`create_and_post_purchase`は認可、Allocation事実の読込、購入作成、購入状態の読込、仕訳情報の読込、購入と仕訳の保存をひとつのPostgreSQL transaction内で順序どおり実行する。Workflow専用の`CreateAndPostPurchaseOperations`は汎用Repositoryではなく、この原子的な業務操作のI/O境界である。能力ごとにtraitを分割してもWorkflowが全能力を必要とし、同じtransaction接続を共有するため、現状ではtrait分割による依存局所化の実益がない。独立したWorkflowや別のtransaction境界から能力を再利用する要件が生じた時点で、用途ごとの狭いtraitへ分割する。

GraphQL境界ではApplication Decisionの業務エラーを入力・状態エラーへ変換し、PostgreSQLのI/O障害と永続化データの破損は内部エラーとして扱う。PostgreSQL Adapter内でも呼び出し側Decisionの不整合と保存済みデータの破損を別のエラーとして表現する。

家計操作の認可は`horse-authorization`の共通契約で判定する。家計のDefault配賦、Poolの作成、負担配賦・資金拠出設定、メンバー・招待・メール転送設定はOWNERのみが管理できる。口座・購入・入金予定・締めなどの家計データ更新は有効なOWNERまたはMEMBERが実行できる。各更新Workflowは同じトランザクションで有効な所属と操作権限を確認する。

購入訂正の`journals.occurred_at`とLedger Entryの日時には訂正を記録した時刻を保存する。`effective_period`は訂正対象として指定したOpen会計期間と月次精算を決める値であり、記録日時を過去へ変更しない。

## 理由

Goの実行コードをRustで一括置換し、GraphQL契約をRustの業務モデルとFrontendに合わせて設計する。Rustへの切り替え時に本番DBを承認済みの新schemaで再作成した。

Atlasを正本にしてDB変更の適用履歴とスキーマを一元管理する。Dieselの型付きDSLはDBアクセスの型検査を提供し、pure DecisionとI/Oの分離は業務判断を外部状態から独立して表現する。

詳細な設計背景と検討事項は[rust.md](./rust.md)を参照する。
