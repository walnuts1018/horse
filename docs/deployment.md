# デプロイと復元

## バックアップの構成

HorseのPostgreSQLデータは共有クラスタ`postgresql-default`に保存されます。CloudNativePGのScheduledBackupはクラスタ全体をSeaweedFSの`cloudnative-pg-backup`バケットへ保存し、WALアーカイブを使った時点復旧に対応します。現在のスケジュールはcron式`0 0 19 */7 * *`、保持期間は7日です。復旧可能な時刻はベースバックアップとWALアーカイブの状態に依存するため、障害対応時に`Backup`リソースとObjectStoreの状態を確認してください。
2026年10月12日のkurumiの読取確認では、ClusterのReady、ContinuousArchiving、LastBackupSucceededがすべてTrueで、ObjectStoreの最終成功バックアップは2026年10月8日19時01分22秒UTC、最初の復旧可能時点は10月1日19時01分18秒UTCでした。
同時点では`Backup`リソースが残っていなかったため、復旧時刻の判断にはObjectStoreの`status.serverRecoveryWindow`も確認します。
これはバックアップ状態の確認であり、復元試験の成功を示すものではありません。

Horseのアップロード原本はSeaweedFSの非公開`horse`バケットに保存されます。バケットではS3 versioningを有効にします。誤上書きや削除後の復元に利用できますが、古いオブジェクトversionを期限削除するlifecycle policyは設定していないため、保存量と費用を定期的に確認してください。versioningは誤削除対策であり、SeaweedFS障害やクラスタ全損に備える独立したオフサイトコピーではありません。

## PostgreSQLからの復元

復元は既存の`postgresql-default`を変更せず、新しい一時CloudNativePGクラスタへ共有クラスタの物理バックアップを復元してからHorseデータを取り出します。既存クラスタのバックアップにはHorse以外のデータベースも含まれるため、復元先を本番クラスタへ直接切り替えないでください。

1. `databases` namespaceの`Backup`リソースで完了した最新のベースバックアップを確認し、CloudNativePGのWAL archiveとSeaweedFS `seaweedfs-store` ObjectStoreが利用可能であることを確認します。予定時刻がバックアップ保持期間を超えている場合は復元できません。
2. `databases` namespaceに一時クラスタ用の別名を付けたCloudNativePG `Cluster`を用意します。`bootstrap.recovery.source`を`seaweedfs-backup`にし、`externalClusters`のpluginに`barmanObjectName: seaweedfs-store`と元クラスタの`serverName: postgresql-default`を指定します。ストレージ、リソース、証明書、SeaweedFSのprojected service account tokenは既存クラスタと同等に設定します。
3. 一時クラスタが復旧したら、そのクラスタへ接続して`horse`データベースの存在、テーブル数、対象データの時刻を確認します。復旧クラスタにはHorse以外のデータも含まれるため、アクセスを制限し、検証後に破棄してください。
4. Horseデータを本番へ戻す場合は、復旧クラスタから`pg_dump -Fc`形式で`horse`データベースを出力します。出力ファイルをアクセス制限された作業環境へ保管し、まず別の検証用データベースへ`pg_restore`して内容を確認します。
5. 本番データベースへの復元は、Horseの書き込みを止め、現行データの退避、復元対象時刻、復旧後の整合性確認方法を決めてから実行します。既存データベースの上書きや削除を含む操作は、別途レビューされた変更手順に従ってください。

## S3原本の復元

削除または上書きしたオブジェクトは、SeaweedFS S3 APIからversioningのversion一覧を確認し、対象キーの復元可能なversionを選んでください。アプリケーションが参照するキーへ戻す前に、別キーへコピーして内容とmetadataを検証します。versioningによる復元操作は本番データを変えるため、対象キーとversion IDを二人で確認してから実行してください。

## 公開probe

Blackbox exporterは`https://horse.walnuts.dev/healthz`を30秒間隔で確認します。`target="horse"`のprobeが5分間連続で失敗すると`HorsePublicProbeFailed` alertを発火します。HorseのPodがまだ存在しないため、このalertの発火とAlertmanagerへの配送は本番環境で未検証です。

## Gemini APIの課金

Gemini APIは無料用と有料用のGoogle Cloud Projectを分け、無料ProjectにはBilling Accountをリンクしません。有料ProjectにはTerraform管理のSpendCapを設定し、Gemini API serviceだけを月500円に制限します。SpendCapは50%、80%、100%でProject Ownersへ通知します。Billing Account administratorsとProject Ownersへの300円到達通知は別のalerts-only Budgetで管理します。
予算期間は[Cloud BillingのUTC-8の暦月](https://docs.cloud.google.com/billing/docs/reference/budget/rest/v1/billingAccounts.budgets)を基準にし、SpendCapで保留したジョブは翌月初の切替後に再試行します。
月初日は解除の反映が遅れた場合に1時間後へ保留し直します。

Google Cloud Free TrialのWelcome creditはGemini APIとAI Studioの利用料に適用されません。Gemini APIのPaid Tierを有効にするにはAI Studioで有料Projectの状態を確認し、Billing Accountのlink後に必要なPrepay設定を完了する必要があります。新規ユーザーはPrepayの利用を求められる場合があり、その場合のcredits購入や支払設定は運用者がAI Studioで行います。TerraformはPrepay購入や自動reloadを設定しません。

SpendCapは請求の見積り遅延を伴い、適用は即時ではありません。Googleの公式説明では請求データ処理に約10分の遅れが発生する場合があり、上限を超えた請求が発生する可能性があります。SpendCapは超過を完全には保証しないため、Workerは`GEMINI_ENABLED=false`の状態を維持し、運用者がBilling状態、SpendCap、AI StudioのPaid Tierを確認した後でのみ有効化します。

## Google CloudのTerraform認証

専用Projectは`walnuts-horse-gemini-free`と`walnuts-horse-gemini-paid`を使用します。組織に属さないProjectをサービスアカウントから新規作成できないため、初回はGoogle ConsoleでProjectを作成し、infraの`google_cloud` moduleでProjectの名前、請求、API、IAM、WIFを定義して取り込みます。既存の`walnuts-dev` Projectも現在の設定を同じmoduleで管理し、Gemini用には使用しません。Googleが変更を許可しない`_Required`のログ設定は管理対象外です。Google provider7.46.1にはGoogleログイン用Web OAuthクライアントの管理リソースがないため、既存の`auth.walnuts.dev`クライアントはConsoleで管理します。登録済みのredirect URIは`https://auth.walnuts.dev/idps/callback`と`https://auth.walnuts.dev/ui/login/login/externalidp/callback`です。

HCP Terraformの`walnuts-dev`組織、`Default Project`、`infra` workspaceだけをWorkload Identity Federationの信頼対象とします。workspace IDとOIDC audienceも照合し、planとapplyのphaseごとに別のサービスアカウントへ短期認証を発行します。長期サービスアカウントキーは作成しません。

計画用アカウントは管理対象ProjectのViewer、有料Projectの予算読取・API quota使用ロール、対象Billing AccountのProject Billing Costs Managerを使用します。ViewerにはAPIキー値の読取権限が含まれるため、Terraformのplanとstateへのアクセスを制限します。適用用アカウントは管理対象ProjectのViewerと、専用ProjectのService Usage Admin、API Keys Adminに加え、有料Projectだけの予算管理ロールとProject Billing Manager、対象Billing AccountのBilling Userを使用します。Owner、Editor、IAM policyの変更権限は付与しません。

初回のWIF、サービスアカウント、カスタムロール、IAM bindingは管理者がConsoleまたはgcloudで設定し、現在値をTerraformコードへ定義してimportします。HCP TerraformのGoogle Cloud認証変数もTerraformで管理します。通常のapplyではこれらの設定を読取できても権限変更はできません。IAMや認証設定に差分が出た場合は適用を止め、管理者が変更内容を確認してbootstrap手順で対応します。通常のapplyを成功させるために権限を自動で追加しないでください。

有料APIキーは月500円のSpendCap作成に成功してから発行し、キーの利用先をGemini APIに限定します。キーは1PasswordのCONCEALEDフィールドへ保存し、External Secretsを通じてWorkerだけへ渡します。Workerの外部HTTPS通信は`generativelanguage.googleapis.com`だけを許可します。DNSとDB、S3、RabbitMQ、OCR、OTelへの内部通信は別途許可します。
