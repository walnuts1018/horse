# Horse UI/UX全面改善指示

## 目的

既存の家計簿アプリケーション「Horse」のUI/UXを包括的にレビューし、実際にコードを修正して、完成度の高いWebアプリケーションに改善してください。

リポジトリ: <https://github.com/walnuts1018/horse>

今回は、機能追加ではなく、**既存機能の使いやすさ、情報の分かりやすさ、視覚的完成度、一貫性を高めること**が目的です。

特に、AIが生成したWebアプリによく見られる、テンプレート的で装飾過多なデザインを避けてください。

目指すのは、シンプルで洗練されており、日常的に快適に使える、高品質な家計管理アプリケーションです。

単にUIレビューを実施して改善案を報告するのではなく、必要な変更をすべて実装してください。

## 1. Skillの活用

以下のSkillを積極的に活用してください。

- `$frontend-design`
- `$web-design-guidelines`
- `$ui-ux-pro-max`

`ui-ux-pro-max-cli`はSkillのインストーラーです。実際の設計・改善作業では、インストールされた`ui-ux-pro-max` Skillの指示と検索機能を使用してください。

それぞれのSkillの内容を読み、次の役割で組み合わせてください。

### frontend-design

- 洗練されたビジュアルデザイン
- 情報の視覚的階層
- タイポグラフィ、余白、配色
- レイアウトの一貫性
- AI生成UIにありがちな没個性的なデザインの回避

ただし、Skillが推奨する独創的なビジュアル表現を無条件に採用しないでください。Horseは日常的に使用する家計管理アプリであり、装飾より実用性を優先します。

### ui-ux-pro-max

- 家計管理アプリに適したUI/UXパターンの調査
- デザインシステムの検討
- 画面ごとの適切な情報構造
- ナビゲーションや入力フォームの改善
- モバイルとデスクトップそれぞれの操作性
- データの可視化や大量の情報表示に適したデザイン

Skillの検索データを実際に活用し、デザイン上の判断に取り入れてください。

ただし、検索結果のスタイルや配色をそのまま適用するのではなく、Horseの既存デザインと要件に合うものを選定してください。

### web-design-guidelines

実装前の問題発見と、実装後のレビューの両方に使用してください。

- アクセシビリティ
- インタラクション
- キーボード操作
- フォームとバリデーション
- レスポンシブデザイン
- 視覚的階層
- フィードバックと状態表示
- Web UIの一般的なベストプラクティス

単にSkillを読み込むだけではなく、実際のコードに適用し、問題を修正してください。

3つのSkillの推奨が矛盾する場合は、Horseのユースケースと実用性を基準に判断してください。

## 2. 最も重要なデザイン方針

### 2.1 ミニマルで洗練されたデザイン

過度な装飾は一切不要です。

以下を避けてください。

- 意味のないグラデーション
- 過剰なシャドウ
- 大きすぎる角丸
- 無意味なカードの多用
- 大きすぎるタイトルや無駄な余白
- 不必要なイラストやアイコン
- 装飾目的のアニメーション
- 不必要なGlassmorphism
- 不自然に派手なアクセントカラー
- 機能と無関係なダッシュボード的装飾

ただし、これらの表現を全面禁止するわけではありません。明確な機能的意義があり、デザイン上も適切な場合は利用して構いません。

見た目を派手にすることと、デザイン品質を高めることを混同しないでください。

既存の落ち着いたグリーン系の配色とNoto Sans JPを基本的に尊重し、必要なら色・タイポグラフィ・余白・境界線などを体系的に調整してください。

### 2.2 UXを最優先

見た目だけの改善で終わらせないでください。

すべての画面で、以下を検討してください。

- ユーザーがその画面で何をしたいのか
- 最も頻繁に行う操作は何か
- 目的を達成するまでに何回操作する必要があるか
- 必要な情報が自然に視界へ入るか
- 説明を読まなくても操作方法が理解できるか
- 入力ミスや誤操作が起きにくいか
- 操作結果が明確に伝わるか
- 情報量が多い場合も使いやすいか

頻繁に使う操作を効率化し、操作ステップや不要な画面遷移を減らしてください。

ただし、重要な確認を省略して誤操作を増やすことは避けてください。

### 2.3 適切な情報密度

家計管理アプリでは、金額、日付、口座、カテゴリ、購入品目、負担割合など、多くの情報を扱います。

情報をカードに分割して大きく表示すれば使いやすくなるわけではありません。

デスクトップでは、一覧性と情報密度を重視してください。特に帳簿や設定などの情報量が多い画面では、テーブルや整列したリストを適切に活用してください。

モバイルでは、単純にデスクトップを縮小するのではなく、限られた表示領域での閲覧と操作を最適化してください。

すべての情報を無理に一画面に詰め込む必要もありません。

### 2.4 デザインの一貫性

アプリ全体で以下を統一してください。

- 色とその意味
- 文字サイズ、ウェイト、行間
- 余白とコンテンツ幅
- ボタンのサイズと重要度
- 入力欄と選択UI
- エラー・成功・警告の表現
- テーブルとリスト
- ダイアログ、ドロワー、ポップオーバー
- アイコンの用途とサイズ
- ナビゲーション
- ホバー、フォーカス、無効状態

必要に応じて既存のCSS変数を整理し、デザイントークンや共通コンポーネントを改善してください。

ただし、抽象化そのものを目的にしないでください。再利用に実益がある部分を適切に共通化してください。

## 3. 既存実装の調査

まず、現在のフロントエンド実装を十分に調査してください。

特に次のファイル・ディレクトリを確認してください。

- `AGENTS.md`
- `README.md`
- `docs/plan.md`
- `docs/completion-audit.md`
- `docs/reviews/ux.md`
- `web/src/app/`
- `web/src/pages/`
- `web/src/shared/ui/`
- `web/src/app/styles/global.css`
- 各ページのCSSおよびCSS Modules

既存のReact、TanStack Start、Relay、Feature-Sliced Design、Base UI、Lucideなどの技術構成を尊重してください。

新しいUIライブラリやCSSフレームワークを無条件に追加しないでください。

また、既存のUXレビューに書かれている問題が現在の実装でも残っているかを確認してください。すでに解決されている問題を重複して修正する必要はありません。

ソースコードだけでは分からない問題を、ブラウザで実際に表示・操作して調査することも重視してください。

## 4. 全画面のUI/UX改善

一部のページだけを改善するのではなく、アプリ全体を対象にしてください。

### ホーム

- 最初に確認すべき家計情報が自然に分かるか
- 月間支出、入金予定、最近の購入記録の優先順位は適切か
- 頻繁な操作へ素早く移動できるか
- ダッシュボードのカードや装飾に無駄がないか
- 情報の視線移動が少ないか

### 帳簿

- 大量の購入記録を効率的に確認できるか
- 購入単位と品目単位の情報構造が分かりやすいか
- 検索、絞り込み、並び替えの操作が直感的か
- 明細の展開、編集、修正、まとめて編集が使いやすいか
- 金額、日付、カテゴリ、購入者などを比較しやすいか
- 選択状態、保存状態、変更内容が分かりやすいか

特に情報密度と操作効率を重視してください。

### 買い物登録

日常的に何度も使用する重要な画面として、優先的に改善してください。

- 店舗名、購入日時、品目、金額、支払元、負担割合の入力順序
- 入力項目の追加・削除・修正
- キーボードによる連続入力
- 商品候補や過去の購入履歴の再利用
- 合計金額と支払金額の整合性表示
- 下書きの保存・復元
- 入力エラーの発見と修正
- スマートフォンのソフトウェアキーボードとの相性

入力のたびに大きく画面をスクロールしたり、不要なタップを繰り返したりしないUIを目指してください。

日本語IMEの変換確定やEnter操作にも注意してください。

### 取り込み

- レシート撮影とファイルアップロードへの導線
- ファイル選択、ドラッグ＆ドロップ
- アップロード・解析・確認の進捗表示
- 読み取り結果の確認と修正
- 原本画像と抽出された情報の照合
- 証拠と購入記録の紐付け
- 解析に失敗した場合のリカバリー
- 処理待ちが複数存在する場合の一覧性

特に、AIやOCRによる読み取り結果が誤っていた場合に、ユーザーが効率的に訂正できるUXを重視してください。

### 精算

- 誰が誰にいくら支払うべきかが一目で理解できるか
- 入金、送金、貸借、返済の区別が明確か
- 精算期間の状態が分かりやすいか
- 誤った金額や口座を選択しにくいか
- 期間を締める操作の影響が理解できるか
- 金銭の移動を二重に記録しないような表示・操作になっているか

会計上の意味を変えず、ユーザーの誤解を減らしてください。

### 分析

- 支出の傾向を素早く把握できるか
- 月別・カテゴリ別・メンバー別などの比較が分かりやすいか
- グラフや集計表が実際の判断に役立つか
- 数値と単位が読みやすいか
- 色だけに依存せずデータを理解できるか
- 不必要なグラフや装飾がないか

グラフを増やすこと自体を目的にしないでください。

### 設定

- 口座、カテゴリ、タグ、予算、定期支出、負担ルール、メンバー管理などを迷わず操作できるか
- 設定項目の分類とナビゲーションが適切か
- 編集、保存、キャンセルの挙動が統一されているか
- 未保存変更が明確か
- 危険な操作と通常操作が区別されているか
- 設定項目が増えても使いやすい構造か

### アプリ共通

サイドバー、ヘッダー、家庭切り替え、通知、ダイアログ、モバイルナビゲーション、ログイン画面などもレビューしてください。

各画面単体ではなく、アプリ全体を通した操作体験を改善してください。

## 5. レスポンシブ・アクセシビリティ

デスクトップとスマートフォンの両方で快適に使用できるUIにしてください。

少なくとも、320px、375px、430px、768px、1280px、1440px程度の画面幅を確認してください。

特に次の点を重視してください。

- 意図しない横スクロールの防止
- 適切な文字サイズとタップ領域
- モバイルでのフォーム入力
- テーブルや大量データの表示
- ダイアログ・ドロワーの画面内表示
- キーボード操作とフォーカス管理
- スクリーンリーダーで理解できるラベル
- 色のコントラスト
- `prefers-reduced-motion`
- 読み込み中・空状態・エラー状態
- 保存や送信などの操作フィードバック

WCAG 2.2 AAを目標にしてください。

## 6. 動作・データの保護

今回はUI/UX改善です。

既存の機能を削除したり、実装を簡略化したりしないでください。

特に以下を維持してください。

- 家計管理のドメインロジック
- 金額計算、負担割合、精算処理
- GraphQL APIとの整合性
- 認証・認可と家庭間のデータ分離
- 購入記録の保存と冪等性
- オフライン・通信失敗時の再送
- 下書き保存と復元
- 既存の検索・フィルター・まとめて編集
- 現在提供されているすべての操作

既存機能を維持したうえで、操作方法や画面構造を変更することは構いません。

重要なのは、使いやすくするために必要な変更を適切に行うことであり、差分を最小化することではありません。

UI改善に不要なバックエンド・データベース・認証基盤の変更は行わないでください。

## 7. 実装と検証の進め方

以下の順序で進めてください。

### Phase 1: 現状調査と設計

1. Skillの内容と既存実装を調査する。
2. 各画面の問題を、重要度と根拠付きで整理する。
3. 機能面・操作性・視覚デザインの問題を区別する。
4. アプリ全体のデザイン方針と共通ルールを決める。
5. 改善対象と実装順序を決定する。

既存の優れた実装は維持してください。問題を作り出してまで変更する必要はありません。

### Phase 2: 共通UIの改善

必要に応じてデザイントークン、タイポグラフィ、共通コンポーネント、ナビゲーション、フィードバック表現などを改善してください。

先に共通部分を整え、各ページのデザインに一貫性を持たせてください。

### Phase 3: 各ページの改善

調査で発見した問題を優先度順に実装してください。

すべてのページを対象にし、画面ごとの主要な操作フローを実際に改善してください。

表面的なCSS調整だけでは解決できない問題については、必要に応じてコンポーネント構造やインタラクションも変更してください。

### Phase 4: 実ブラウザでの検証

可能な限り、実際に開発サーバーを起動し、Playwrightなどで画面を表示・操作してください。

- デスクトップとモバイルのスクリーンショット確認
- 主要なユーザーフローの操作
- キーボード操作
- 入力エラーと再試行
- データが多い場合の表示
- 長い日本語テキストの表示
- ローディング・空状態・エラー状態

実ブラウザで発見した問題を修正し、再度確認してください。

安全な開発用データまたは合成データを使用してください。実運用データに対する購入・送金・精算などの変更操作は行わないでください。

認証や環境の制約によって検証できない箇所は、未検証であることを明示してください。

### Phase 5: 最終レビュー

`web-design-guidelines`を再度適用し、変更後のUIをレビューしてください。

視覚的な一貫性、操作性、アクセシビリティ、レスポンシブ対応について問題が残っていれば修正してください。

既存のテスト、型検査、Lint、ビルドも実行してください。

必要に応じてUIの回帰テストを追加してください。ただし、テスト基盤の導入自体が目的にならないようにしてください。

## 8. 完了条件

以下を満たすまで改善を続けてください。

- 主要画面のUI/UXレビューと必要な改善が完了している
- 既存の操作・機能に退行がない
- アプリ全体のデザインに一貫性がある
- 過剰な装飾がない
- 日常的な操作が自然かつ効率的に行える
- デスクトップとスマートフォンで快適に利用できる
- アクセシビリティ上の重大な問題がない
- 型検査、Lint、テスト、ビルドが成功する
- 実ブラウザで可能な主要操作を検証している

作業完了時には、改善した内容、重要な設計判断、実施した検証、残っている未検証事項を日本語で簡潔に報告してください。

**最も重視するのは、ユーザーが毎日使いたくなる、シンプルで直感的かつ完成度の高い家計管理アプリケーションにすることです。**

Skillを適用すること自体を目的にせず、最終的なUI/UXの品質を判断基準として作業してください。
