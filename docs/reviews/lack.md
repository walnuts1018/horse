# Horseの実装・機能レビュー

結論として、追加・修正した方がよい部分はあります。ただし、会計モデルや技術構成を作り直す必要はありません。現状は、基本機能の不足よりも、取り込みから記帳までの未接続部分を解消する方が効果的です。

GitHubの`main`を対象に、GraphQL、GoのApplication Service、取り込み処理、Web UI、テスト、完成判定書を照合しました。今回は静的レビューであり、実際のデプロイ環境で操作・テストを実行したわけではありません。

## 1. 優先して修正したい項目

P1

カード・銀行明細の未対応取引種別が会計処理へ未接続

カード引落し、外部入金、貸付・返済などの明細行は、対応する記帳APIへ未接続です。口座間振替は、単一文書内の明細行を口座移動へ紐付け、振替元と振替先の仕訳、確認状態を同一トランザクションで記録します。同じ明細行の再送は拒否します。一方、同じ実取引が別文書にも記載された場合の重複照合は未実装です。

## 2. そのほかに確認できた実装上の不足

| 優先度 | 項目 | 現状と必要な対応 |
| --- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| P1 | メールの自動取り込み | EMLのアップロード・本文解析・添付展開は実装済みですが、Gmailからの定期取得や、専用アドレスへのメール転送を自動受信する機能は確認できません。現状は利用者がファイルをアップロードする必要があります。 |
| P1 | 家庭メンバーの管理 | 招待・参加・招待取り消し、参加済みメンバーの除名、本人の脱退は実装されています。オーナー移譲は未実装です。 |
| P2 | 定期支出の実績管理 | 定期支出の登録と月額換算はありますが、支払期日の到来、購入実績との照合、未払いの表示、次回予定日の更新を連携する仕組みは見当たりません。定期支出を本格的に管理するなら追加する価値があります。 |
| P2 | 保存済み原本の管理 | アップロード前のファイル削除はできますが、保存済み原本の削除・保存期限管理・関連する購入との整合的な削除は確認できません。取り込みを長期運用するなら必要です。 |
| P3 | Gemini無料枠の利用効率 | 無料優先ルーティングと429時の再試行はあります。一方、モデル別のRPM・TPM・RPDの共有管理や、バックグラウンド処理のFlex／Batchへの振り分けは十分には活用されていません。費用最適化として後から改善できます。 |

## 3. 運用設定

通常Workerの`GEMINI_ENABLED`は`false`です。この設定では通常の取り込みで画像・PDFのAI解析jobを処理しません。Geminiを通常利用する場合は、Spend Capを維持したうえでWorker設定を有効にする必要があります。

## 4. 現状維持でよい部分

会計台帳、負担と決済の分離、複数プール、資金拠出ルールのスナップショット、締め後の訂正、貸付・返済・贈与、冪等性、オフライン下書き、商品正規化、予算と分析、Relay/gqlgenの構成については、今回確認した範囲で大規模な再設計が必要な理由は見つかりませんでした。

実装済みの機能をさらに細分化したり、ライブラリを置き換えたりすることも、現時点では優先しなくてよいと思います。

## 推奨する作業順序

まずはカード引落し、外部入金、貸付・返済などの未対応種別を既存の記帳APIへ接続し、別文書間の口座間振替の重複を検出する方法を決めるのがよいです。明細の二重計上を防ぎ、取引種別に応じた仕訳を一度だけ作成する必要があります。

次に、メール自動取り込みと照合UIを完成させるのが合理的です。

Horseは「主要機能がまだ揃っていない」段階ではありません。むしろ、揃っている機能同士を正しくつなぎ、実運用で信頼できる状態にする段階だと評価します。
