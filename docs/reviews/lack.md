# Horseの実装・機能レビュー

結論として、追加・修正した方がよい部分はあります。ただし、会計モデルや技術構成を作り直す必要はありません。現状は、基本機能の不足よりも、取り込みから記帳までの未接続部分を解消する方が効果的です。

GitHubの`main`を対象に、GraphQL、GoのApplication Service、取り込み処理、Web UI、テスト、完成判定書を照合しました。今回は静的レビューであり、実際のデプロイ環境で操作・テストを実行したわけではありません。

## 1. 優先して修正したい項目

P1

カード・銀行明細の取引種別のうち、返金以外が会計処理へ未接続

カード明細の`REFUND`は、利用者が選択した確定済み購入または品目への訂正として保存できるようになりました。返金額と原本領域・抽出内容は最新の成功した抽出結果から取得し、訂正、明細確定、証拠を同一トランザクションへ保存します。Testcontainers PostgreSQL 18の`TestCorrectPurchaseFromStatementKeepsRowEvidenceAtomic`で冪等再試行、重複行拒否、過剰返金のrollback、世帯分離を確認しています。

カード引落し、口座間振替、外部入金、貸付・返済など、`CARD_PURCHASE`と`REFUND`以外の明細行を対応する記帳APIへ接続する処理は未実装です。引落しを支出として二重計上しないことや、口座間振替の両側を一度だけ記帳することを含め、取引種別ごとの対応が必要です。

## 解決済み項目

PDF・画像のアップロードではレシート、注文履歴、カード明細、銀行明細を選択でき、選択内容はアップロード後の表示とAPIへの送信に反映されます。CSVではカード明細または銀行明細を選択でき、EMLはメールとして扱います。

カード明細の購入行は決済口座を明示的に選ぶ必要があり、口座未選択では記帳できません。

## 3. 実装不足ではなく、動作確認が残っている部分

[完成要件と検証](https://github.com/walnuts1018/horse/blob/main/docs/completion-audit.md) によると、次の部分はコードやテストが存在しますが、実際の利用環境での検証が十分ではありません。

- Geminiを使った通常のレシート取り込み：Free／Paid双方のAPI呼び出しは確認されていますが、通常Workerの`GEMINI_ENABLED`は`false`に戻されています。通常の利用経路では画像・PDFのAI解析が動かない状態です。
- 日本語の実レシートに対する精度：混在税率、端数、値引き、ポイント、複数決済について、本物のレシートを用いた評価が不足しています。
- 実際の複数ユーザー利用と復元：家庭への他ユーザー参加、オフライン競合、PostgreSQLとS3の復元試験などは、完成を裏付ける検証が残っています。

これらは、同じ機能を再実装する話ではありません。実装済みの経路を実データで評価し、必要な箇所だけ改善するのが適切です。

## 4. 現状維持でよい部分

会計台帳、負担と決済の分離、複数プール、資金拠出ルールのスナップショット、締め後の訂正、貸付・返済・贈与、冪等性、オフライン下書き、商品正規化、予算と分析、Relay/gqlgenの構成については、今回確認した範囲で大規模な再設計が必要な理由は見つかりませんでした。

実装済みの機能をさらに細分化したり、ライブラリを置き換えたりすることも、現時点では優先しなくてよいと思います。

## 推奨する作業順序

まずはカード引落し、口座間振替、外部入金、貸付・返済など、返金以外の明細取引種別を既存の記帳APIへ接続するのがよいです。明細の二重計上を防ぎ、取引種別に応じた仕訳を一度だけ作成する必要があります。

次に、Geminiを使った取り込みを通常環境で有効化して実レシートを評価し、その結果を踏まえてメール自動取り込みと照合UIを完成させるのが合理的です。

Horseは「主要機能がまだ揃っていない」段階ではありません。むしろ、揃っている機能同士を正しくつなぎ、実運用で信頼できる状態にする段階だと評価します。
