# Horseの実装・機能レビュー

結論として、追加・修正した方がよい部分はあります。 ただし、会計モデルや技術構成を作り直す必要はありません。現状は、基本機能の不足よりも、取り込みから記帳までの未接続部分と、一部の集計上の不具合を解消する方が効果的です。

GitHubの`main`を対象に、GraphQL、GoのApplication Service、取り込み処理、Web UI、テスト、完成判定書を照合しました。今回は静的レビューであり、実際のデプロイ環境で操作・テストを実行したわけではありません。

## 1. 優先して修正したい項目

P0

分析画面で選択期間の最終月が集計から漏れる

[use-analysis-data.ts](https://github.com/walnuts1018/horse/blob/main/web/src/pages/analysis/model/use-analysis-data.ts) では購入履歴の終了日時を `${toMonth}-01T00:00:00+09:00` にしています。一方、[query_purchases.go](https://github.com/walnuts1018/horse/blob/main/internal/graph/query_purchases.go#L94-L108) は終了日時を排他的な条件（`occurred_at < to`）として扱っています。

例えば2026年5〜10月を選ぶと、商品・店舗・プール・決済元の分析では10月の購入が丸ごと除外されます。カテゴリ・メンバーの分析は別の集計APIなので、この不具合の直接の対象ではありません。

修正: 終了日時を最終月の翌月1日00:00にし、月境界のテストを追加してください。

P1

カード・銀行明細の取り込み後、会計処理へつながらない取引種別がある

[statement.go](https://github.com/walnuts1018/horse/blob/main/internal/ingestion/statement.go) では返金、カード引落し、口座間振替、未分類などを識別できます。しかし、[use-import-confirmation.ts](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/model/use-import-confirmation.ts) の確定処理は `CARD_PURCHASE` に限られています。

既に貸付・返済・口座間移動・外部入金を記帳するAPIは存在するので、明細の取引種別に応じて既存処理へ接続するのがよいです。

特に、クレジットカードの引落しを新しい支出として二重計上しないこと、返金を元購入と対応付けることが重要です。

P1

PDF・画像のカード明細／銀行明細をUIから正しく取り込めない

[imports.ts](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/model/imports.ts) の`sourceKind()`はCSV以外のPDF・画像を基本的に`receipt`と判定します。アップロード時の種別選択UIもCSVにしかありません。

バックエンドはカード・銀行明細のPDFや画像解析に対応しているため、取り込み画面の種別指定が足りない状態です。

修正: 画像・PDFにも「レシート／注文履歴／カード明細／銀行明細」を指定できるようにし、誤分類後の変更にも対応させてください。

## 2. そのほかに確認できた実装上の不足

| 優先度 | 項目 | 現状と必要な対応 |
| --- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| P1 | 決済口座の誤登録防止 | カード明細から購入を確定すると、[use-import-confirmation.ts](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/model/use-import-confirmation.ts#L321-L347) は `household.accounts[0]` を決済元に使用します。カード末尾番号と口座を照合するか、確定前に口座選択を必須にすべきです。誤った口座へ記帳される可能性があります。 |
| P1 | メールの自動取り込み | EMLのアップロード・本文解析・添付展開は実装済みですが、Gmailからの定期取得や、専用アドレスへのメール転送を自動受信する機能は確認できません。現状は利用者がファイルをアップロードする必要があります。 |
| P1 | 家庭メンバーの管理 | 招待・参加・招待取り消しはありますが、参加済みメンバーの除名、脱退、オーナー移譲は見当たりません。[member.graphql](https://github.com/walnuts1018/horse/blob/main/graphql/member.graphql) と[設定画面](https://github.com/walnuts1018/horse/blob/main/web/src/pages/settings/ui/settings-members-section.tsx) も一覧表示のみです。 |
| P2 | 過去の購入との証拠照合 | [observation-linker.tsx](https://github.com/walnuts1018/horse/blob/main/web/src/pages/ledger/ui/observation-linker.tsx#L47-L80) は既存購入を直近100件だけ取得します。古い購入に証拠を紐付けるには、検索とページングが必要です。 |
| P2 | 定期支出の実績管理 | 定期支出の登録と月額換算はありますが、支払期日の到来、購入実績との照合、未払いの表示、次回予定日の更新を連携する仕組みは見当たりません。定期支出を本格的に管理するなら追加する価値があります。 |
| P2 | 保存済み原本の管理 | アップロード前のファイル削除はできますが、保存済み原本の削除・保存期限管理・関連する購入との整合的な削除は確認できません。取り込みを長期運用するなら必要です。 |
| P3 | Gemini無料枠の利用効率 | 無料優先ルーティングと429時の再試行はあります。一方、モデル別のRPM・TPM・RPDの共有管理や、バックグラウンド処理のFlex／Batchへの振り分けは十分には活用されていません。費用最適化として後から改善できます。 |

特に決済元に最初の口座を暗黙に使う問題は、機能追加より優先して修正したいです。家計簿では、購入金額が合っていても支払元が間違えば残高や精算結果が誤ります。

## 3. 実装不足ではなく、動作確認が残っている部分

[完成要件と検証](https://github.com/walnuts1018/horse/blob/main/docs/completion-audit.md) によると、次の部分はコードやテストが存在しますが、実際の利用環境での検証が十分ではありません。

- Geminiを使った通常のレシート取り込み：Free／Paid双方のAPI呼び出しは確認されていますが、通常Workerの`GEMINI_ENABLED`は`false`に戻されています。通常の利用経路では画像・PDFのAI解析が動かない状態です。
- 日本語の実レシートに対する精度：混在税率、端数、値引き、ポイント、複数決済について、本物のレシートを用いた評価が不足しています。
- 実際の複数ユーザー利用と復元：家庭への他ユーザー参加、オフライン競合、PostgreSQLとS3の復元試験などは、完成を裏付ける検証が残っています。

これらは、同じ機能を再実装する話ではありません。実装済みの経路を実データで評価し、必要な箇所だけ改善するのが適切です。

## 4. 現状維持でよい部分

会計台帳、負担と決済の分離、複数プール、資金拠出ルールのスナップショット、締め後の訂正、貸付・返済・贈与、冪等性、オフライン下書き、商品正規化、予算と分析、Relay/gqlgenの構成については、今回確認した範囲で大規模な再設計が必要な理由は見つかりませんでした。

実装済みの機能をさらに細分化したり、ライブラリを置き換えたりすることも、現時点では優先しなくてよいと思います。

## 推奨する作業順序

まずは、①分析の月境界修正 → ②明細の決済元確認 → ③銀行・カード明細の全取引種別の記帳対応 → ④PDF・画像の原本種別指定を修正するのがよいです。いずれも既存機能の正しさや利用可能性に直結します。

次に、Geminiを使った取り込みを通常環境で有効化して実レシートを評価し、その結果を踏まえてメール自動取り込みと照合UIを完成させるのが合理的です。

Horseは「主要機能がまだ揃っていない」段階ではありません。むしろ、揃っている機能同士を正しくつなぎ、実運用で信頼できる状態にする段階だと評価します。
