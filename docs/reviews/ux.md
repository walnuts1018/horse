# horse UI/UX徹底レビュー

対象：[walnuts1018/horse](https://github.com/walnuts1018/horse) 確認ブランチ：`main` / `778cb41`

今回はデザインの好みよりも、入力・修正・確認に必要な操作数を減らすことを最優先に、実際のReactコンポーネントと状態管理を確認しています。

すでに実装されている良い機能もあります。連続した品目入力、IMEの変換中Enterへの対応、購入単位での店名・日時・決済元の共有、下書きの自動保存、商品サジェスト、複数品目の一括変更、原本画像との照合などです。

したがって、これらを新機能として再提案するのではなく、既存機能をより少ない操作で使えるようにすることと、実装上の問題の修正に絞ります。

なお、これは現行ソースコードに基づくレビューです。ブラウザ上で実際に操作した結果や、実機で測定した操作時間ではありません。

### 1-1. カテゴリを選択しても、品目に正しく設定されない可能性がある

重大度：高 · 手入力

対象：[edit-purchase-items.tsx:109–153](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/ui/edit-purchase-items.tsx#L109-L153)

`updateCategory`では次の処理をしています。

```
const updateCategory = useCallback(
  (id: string) => {
    setUserCategoryId(id);
    patchDraft({ categoryId: id });
  },
  [patchDraft],
);
```

しかし`patchDraft`が呼ぶ`update`では、`effectiveCategoryId`で再度上書きしています。

```
const withEffectiveCategory = {
  ...next,
  categoryId: effectiveCategoryId,
};
```

Reactのstate更新は即座に反映されるとは限らないため、ここで使われる`effectiveCategoryId`は古い値です。

つまり、カテゴリの`select`には選択結果が表示されていても、内部の`draft.categoryId`が以前の値のままになる可能性があります。

そして品目の確定時には、その`draft.categoryId`が使われています。

[addItemの実装](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/ui/edit-purchase-items.tsx#L248-L272)

改善方法

`categoryId`の実際の入力状態を1か所に統一してください。

ユーザー選択値をstateに持ち、自動推定値を導出する方式は維持できます。ただし、品目を追加する際には、表示されている実効カテゴリを直接使用するべきです。

また、`setUserCategoryId`直後の古い導出値で入力を上書きしないようにしてください。

この問題は、商品候補の選択時にも影響し得ます。

### 1-2. AI取り込み後の負担割合が編集できない

重大度：高 · AI入力

対象：[receipt-review.tsx:240–389](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/ui/receipt-review.tsx#L240-L389)

AI取り込みの品目編集には、品名、カテゴリ、商品、金額、数量などの入力欄があります。

しかし、品目別の負担割合を編集するUIがありません。

さらに確定処理では、各品目の`allocations`に`null`を渡しています。

[use-import-confirmation.ts:326–356](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/model/use-import-confirmation.ts#L326-L356)

例えば、スーパーで次の商品を購入したとします。

| 商品 | 希望する負担 |
| --------- | ----------- |
| 牛乳 | A60% / B40% |
| ヨーグルト | A60% / B40% |
| A個人のシャンプー | A100% |
| B個人の衣服 | B100% |

現状のAI確認画面からは、最後の2商品を希望する負担割合に変更して確定できません。

確定後に帳簿へ移動し、別の編集機能から修正する必要があります。

改善方法

レシートの品目一覧にも、手入力と同じ負担割合コンポーネントを配置します。

標準割合の品目は「標準」とだけ表示し、変更したい品目ではポップオーバーから直接変更できるようにします。

さらに、複数品目を選択して一括変更できるようにします。

これは最優先で対応するべきです。

### 1-3. 既存の購入を修正するとき、品目ごとに保存しなければならない

重大度：高 · 帳簿編集

対象：

- [purchase-item-editor.tsx:98–151](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/ledger/ui/purchase-item-editor.tsx#L98-L151)
- [ledger-page.tsx:518–587](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/ledger/ui/ledger-page.tsx#L518-L587)

現在、購入を編集モードにすると、各品目に「品目を保存」ボタンが現れます。

例えば、AIが認識した20品目のうち、5品目の名前や金額を修正したい場合、品目ごとに保存操作が必要です。

これはかなり使いづらいと思います。

改善方法

購入全体を1つの編集セッションとして扱います。

品名、カテゴリ、商品、金額、負担割合などは、それぞれ編集した瞬間にクライアントの下書きに反映します。

最後に「変更を保存」を1回押すだけで済むようにします。

バックエンドには、変更された品目だけをまとめて渡すBulk Updateを使用するか、購入編集セッション用の原子的な更新APIを用意します。

既存の一括更新機能を利用できる部分は再利用してください。

また、変更のない場合に保存ボタンを押す必要がないことを明確にし、入力の途中で画面を閉じた場合にも編集内容を復元できるようにすると、さらに使いやすくなります。

### 1-4. 1品目だけの金額修正が、ほかの品目の税計算候補まで無効化する

重大度：高 · AI入力の正確性

対象：

- [receipt-review.tsx:284–299](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/ui/receipt-review.tsx#L284-L299)
- [use-import-confirmation.ts:120–130](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/model/use-import-confirmation.ts#L120-L130)

金額を編集すると、次の状態が設定されます。

```
setManualAmountOverrides((current) => ({
  ...current,
  [selectedDocument.id]: true,
}));
```

これはレシート全体に対するフラグです。

そして金額を計算する関数では、次の条件分岐を使っています。

```
return manualAmountOverrides[document.id]
  ? item.grossAmount
  : (candidate?.amounts[index] ?? item.grossAmount);
```

このため、1品目だけの金額を手動修正すると、ほかの全品目についても選択中の計算候補の金額を使わなくなります。

たとえば10品目のうち1品目を修正しただけで、残り9品目の税計算結果まで変わる可能性があります。

改善方法

手動修正状態をレシート単位ではなく、品目の安定ID単位で管理してください。

金額の優先順位は次のようにします。

`その品目の手動修正 > 選択された計算候補 > AI抽出額`

さらに、金額が修正されたときは、全品目の税計算を自動的に無効化するのではなく、整合性検証を再実行します。

### 1-5. レシート撮影からAI解析までの確定操作が多い

重大度：中〜高 · モバイル

対象：

- [camera-capture.tsx:174–320](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/ui/camera-capture.tsx#L174-L320)
- [imports-page.tsx:153–216](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/ui/imports-page.tsx#L153-L216)

現在は次の流れになっています。

撮影ボタン

カメラで撮影

画像確認 → 「画像を追加」

アップロード待ち → 「アップロード」

画像の確認画面自体は良いです。しかし、そこで「画像を追加」を押した後に、さらにアップロードを開始しなければならないのは余計な操作です。

改善方法

画像を確認して「取り込む」を押した時点でアップロード・AI解析を自動開始してください。

複数枚撮影するときは、撮影した画像を順次キューへ追加し、次の撮影を続けながらアップロードを実行します。

必要であれば「複数枚を1つのレシートとして扱う」操作を用意します。

画像を撮影しただけで原本がクラウドへ送信されることを避けたい場合は、撮影後の1回の明示確認を残せば十分です。

## 2. 手入力をさらに速くする改善

この領域は細かな改善を積み重ねる価値が特に高いです。毎日の入力で発生する操作だからです。

### 2-1. 品目を続けて入力すると、直前の購入が完了したタイミングで画面遷移する可能性がある

重要度：高

[horse-app.tsx:300–352](https://github.com/walnuts1018/horse/blob/778cb41/web/src/app/horse-app.tsx#L300-L352)

購入を送信キューに入れた後、画面をリセットする実装はあります。

しかし、サーバーへの送信が完了すると、`autoNavigateKey`を使って帳簿画面へ遷移する処理もあります。

このため、1件目を保存した直後に2件目の入力を開始すると、1件目の送信完了によって画面遷移が発生する可能性があります。未保存の変更があれば、破棄確認ダイアログが表示される可能性もあります。

これは連続入力を妨げます。

改善案： 保存完了時の遷移先をユーザーの操作に結びつけます。「保存して続ける」と「保存して帳簿へ」を選べるようにし、いったん次の入力を開始した後は、古い送信結果によって画面を移動させないようにしてください。

### 2-2. 買い物を保存すると、店名と決済元が初期状態に戻る

重要度：中

[purchase-create-page.tsx:175–182](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/ui/purchase-create-page.tsx#L175-L182)

保存後に店名を空文字へ戻し、決済元もリセットしています。

異なる店舗へ移動したなら問題ありませんが、同じ店舗の買い物を分割して記録する場合には再入力が必要です。

改善するなら、保存後に「同じ店で続ける」を設けるか、保存して続ける操作では店名と決済元を保持する方式がよいです。日時は現在時刻へ更新します。

さらに、決済元は直前の選択を保持する設定を用意すると、普段使うカードを毎回選び直す必要がなくなります。

### 2-3. 決済元の初期値が配列の先頭になっている

重要度：高

[purchase-payments.ts:55–64](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/model/purchase-payments.ts#L55-L64)

```
paymentAccountId: household.accounts[0]?.id ?? ""
```

これでは、ユーザーの利用傾向と関係なく先頭の決済元が設定されます。

最初に作成した銀行口座と、日常的に使用するクレジットカードが異なる場合、毎回選び直さなければなりません。

逆に、変更し忘れて誤った口座で記録する可能性もあります。

改善案： 次の優先順位を推奨します。

`同じ店舗で直近に使った決済元 → ユーザーが最後に使った決済元 → 明示設定した標準決済元`

ただし、曖昧な場合は確信のない推定を勝手に確定しないようにします。変更したことがある決済元を優先的に候補へ出すだけでも効果があります。

### 2-4. 「同じ店で入力」「前回の購入をコピー」の導線が離れている

重要度：中

[edit-purchase-details.tsx:73–118](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/ui/edit-purchase-details.tsx#L73-L118)

履歴コピーは実装済みですが、独立したパネルになっています。

特にモバイルでは購入情報の後に履歴パネルが配置され、品目入力領域から離れています。

直近の買い物をコピーしたいだけなのに、履歴パネルを探して移動する必要があります。

改善案： 店名入力欄の近くに関連する候補をまとめます。

例えば、店名を「イオン」にしたら、その店舗での直近購入を1件だけ「前回の買い物を使う」として表示します。

履歴の全件表示は必要になった場合だけ開けば十分です。

### 2-5. 品目が入力途中でも、購入を一括確定できるようにする

重要度：中

[購入確定ボタン](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/ui/purchase-create-page.tsx#L289-L296)

現在、品目は「追加する」という操作によってリストへ移動します。

1品目しか買っていない場合でも、品名と金額を入力したあとに「品目を追加」、さらに「保存して送信」を押す必要があります。

改善案： 購入の保存を押した際、入力途中の品目が有効なら、その品目も自動的に含めて保存します。

これによって、1品目の買い物なら最後の「品目を追加」が不要になります。

不完全な品目がある場合は、その入力を消さずに該当欄へ案内します。

### 2-6. 空の品名欄でEnterを押すと、意図せずフォーム送信する可能性がある

重要度：高

[キーボード操作](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/ui/edit-purchase-items.tsx#L291-L339)

品名入力でEnterを処理する条件には、`draft.itemName.trim()`があります。

そのため、品名が空のときはEnterの既定動作が残ります。

HTMLフォームには送信ボタンがあるため、すでにいくつか品目を追加している状態で空の品名欄でEnterを押すと、意図せず購入の確定に進む可能性があります。

改善案： 入力欄でのEnterの意味を明確にしてください。

品名がある場合は金額入力へ移動。空の場合は何もしない。購入全体の保存は明示的な確定操作だけで実行します。

### 2-7. 日本語IME変換中の矢印キーを候補操作が奪う可能性がある

重要度：高

同じファイルの[291–306行](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/ui/edit-purchase-items.tsx#L291-L306)では、上下矢印キーを商品サジェストの選択に使用しています。

しかし、上下矢印とEscapeの分岐にIME変換中のガードがありません。

日本語変換中に候補を上下キーで選びたい場合、アプリ側のサジェストがキーを奪ってしまう可能性があります。

Enterには既に`isComposing`のチェックがあるので、同じ考慮を矢印キーとEscapeにも適用してください。

### 2-8. 品目追加のUndoが1段階しかない

重要度：中

[Undoとコピーの実装](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/ui/edit-purchase-items.tsx#L160-L205)

現在は`undoItems`という単一のスナップショットを保持しています。

したがって、直前の操作を1回戻すことはできますが、その前の操作に戻ることはできません。

複数品目を編集していた場合には不便です。

改善するなら、操作単位のUndo/Redo履歴を持たせます。

ただし、1文字入力するたびに履歴を作る必要はありません。品目追加、削除、負担変更、一括編集などを操作単位としてまとめます。

さらに、購入履歴からコピーした場合には、品目だけでなく同時に変更された店名も同じUndo操作で戻すべきです。

### 2-9. 貼り付け時の金額にカンマが含まれると、誤って解析する可能性がある

重要度：高

[貼り付け解析](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/ui/edit-purchase-items.tsx#L396-L427)

現在の分割処理は次のとおりです。

```
line.split(/\t|,(?=\s*\d)/)
```

例えば、TSVで次の内容を貼り付ける場合です。

```
ヨーグルト 1,280
牛乳 248
```

金額内のカンマまで区切り文字として認識されるため、1,280円が1円として扱われる可能性があります。

改善案： TSVとCSVを適切に区別して解析します。CSVではクォートにも対応し、解析に失敗した行を黙って破棄しないようにします。

複数行の貼り付け後は「2品目追加しました」のような通知を表示し、無視された行がある場合だけ確認を促します。

### 2-10. 負担割合を1タップで変更できるようにする

重要度：高

[負担割合のポップオーバー](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/ui/edit-purchase-item-allocations.tsx#L31-L79)

現在は、プールごとの比率を数値入力する形式です。

これは自由度が高い一方、A100%、B100%、半分ずつなどのよくある変更でも、数値入力が必要です。

例えばA60%、B40%からA100%に変更したいだけなら、次のような操作で済ませたいです。

負担割合のクイック選択案

標準 60:40

A 100%

B 100%

50:50

上記は操作の配置案です。よく使う割合を優先し、「自由に設定」は別に用意します。

また、プールが2つだけなら、片方を60%に変更した際にもう片方を40%へ自動調整するモードがあると便利です。

独立した比率入力は必要な場合に残します。

### 2-11. 負担表示に実際の割合が出ない

同じコンポーネントの[allocationName()](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/purchase-create/ui/edit-purchase-item-allocations.tsx#L18-L29)では、複数プールへの負担時にプール名を`/`で連結しています。

しかし、実際の比率が表示されません。

A:B=3:2なのか1:1なのか、開かなければ分からない状態です。

複数プールでは、`A60% / B40%`のように表示するほうが直感的です。

また、`JSON.stringify`でデフォルト配分と比較している部分は、要素の順序が違うだけでも標準設定と判定されません。プールIDと比率を正規化して比較するべきです。

### 2-12. 新規購入の品目にも一括編集機能が必要

現在、帳簿の既存品目には一括編集機能があります。しかし、新規購入の入力グリッドには複数選択による一括編集がありません。

例えば10品目入力した後で、5品目の負担割合をA100%にしたい場合、5品目のポップオーバーをそれぞれ操作する必要があります。

改善案： 新規購入でも、品目選択からカテゴリ・負担・削除を一括操作できるようにします。

PCではShiftで範囲選択、スマホでは選択モードと下部アクションバーを用意するとよいです。

## 3. AI取り込みの確認UI

ここは単純な入力速度以上に、誤認識を少ない操作で安全に訂正することが重要です。

### 3-1. モバイルで原本画像が編集欄より先に長く表示される

重要度：高

対象：

- [import-document-review.tsx](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/ui/import-document-review.tsx#L125-L167)
- [モバイルレイアウト](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/ui/imports-page.module.css#L193-L207)

PCでは原本画像と編集欄が左右に並ぶよう設計されています。これは適切です。

しかし、幅900px未満では1列になり、原本プレビューが編集欄の前に表示されます。

原本プレビュー内には、画像だけでなく範囲の再抽出やOCR行一覧もあります。

このためスマホでは、必要な編集欄に到達するまでスクロールが長くなる可能性があります。

改善方法

モバイルでは原本画像をコンパクトなプレビューにして、品目編集欄へすぐアクセスできるようにします。

ある品目を編集したときだけ、対応する原本領域をその品目の近くに拡大表示する方式がよいです。

全文OCRやクロップ座標などの詳細機能は、通常の確認フローとは別の展開領域へ移します。

### 3-2. 品目を編集しても、原本側の対応位置が自動的に選択されない

[品目編集フォーム](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/ui/receipt-review.tsx#L240-L299)

原本画像上の領域をクリックして選択する機能はあります。

しかし、品目の名前や金額の入力欄にフォーカスしたときに、対応する原本領域を選択する連携は見当たりませんでした。

これでは、原本側から品目を選択することはできても、編集対象から原本を探す操作が十分に省略できません。

PCでは入力欄へのフォーカスと原本のハイライトを双方向に同期させ、モバイルでは対応する画像領域を近くに表示してください。

### 3-3. 商品候補の検索方法がネイティブselectと噛み合っていない

重要度：中

[product-variant-select.tsx](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/ui/product-variant-select.tsx#L30-L96)

商品候補の取得は、`select`にフォーカスしたタイミングで開始されます。

しかも220msのデバウンスがあります。

そのため、ユーザーが選択欄を開いた直後には候補がまだ存在しない可能性があります。特にスマホのネイティブselect UIでは、開いている最中に候補が追加される操作感が安定しない場合があります。

改善方法

商品候補は品目表示時点で取得するか、候補欄を開く直前までにプリフェッチしてください。

商品数が多い場合は、ネイティブselectではなく検索可能なComboboxが適しています。

すでに紐付け済みの商品を再選択させず、現在の選択を明示することも重要です。

### 3-4. 金額を修正しただけで、訂正理由を手入力する必要がある

重要度：中

[金額の訂正理由検証](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/model/use-import-confirmation.ts#L291-L324)

手動金額修正などの場合、訂正理由が3文字以上必要です。

監査目的は理解できますが、OCRで1文字読み間違えた金額を直すたびに自由記述を要求すると、確認操作が増えてしまいます。

改善案： 訂正理由を選択式にします。

「OCRの読み間違い」「割引・税の修正」「レシートの印字が不明瞭」「その他」といった選択肢を用意し、通常は1タップで完了するようにします。

訂正前後の値、原本位置、操作者は自動保存してください。

### 3-5. 計算候補の選択を毎回要求するのは避ける

同ファイルでは、計算候補が存在していて未選択の場合、確認時にエラーとなります。

候補が1つしかなく、レシート全体の整合性も確認できている場合には、利用者に選択操作を求める必要はありません。

明確に一意な候補は初期選択し、複数の妥当な候補が存在する場合だけ人間に判断を求める方式がよいです。

ただし、合計額が一致するだけで、税の解釈まで確定できるわけではありません。そのため、UIでは「計算が一致」と「税の解釈まで確定」を区別するべきです。

### 3-6. AI確認画面で品目追加・削除ができない

重要度：高

[receipt-review.tsx](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/ui/receipt-review.tsx#L240-L389)

AI確認画面では抽出された品目の編集はできますが、通常の手入力フォームのように品目を新規追加したり、誤認識された余分な品目を削除したりする操作が見当たりません。

これでは、AIが1品目を見落とした場合にその場で修正できません。

改善案： AI確認画面を、手入力と共通の品目エディタで構築するのが理想的です。

AI入力時だけ証拠領域、認識の信頼度、印字額などを追加表示します。

「AIの確認」と「手入力」を別々の編集機構として保守するよりも、操作が統一され、ユーザーが学ぶことも減ります。

### 3-7. 「確認が必要な項目」のUIをさらに整理する

[reviewTargets](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/imports/model/use-import-confirmation.ts#L161-L227)

確認対象を抽出し、「前へ」「次へ」で順番に移動できる実装は良いです。

改善するとしたら、各対象を確認したかどうかを明示的に管理することです。

現在のロジックでは、`verification`や`confidence`などによって確認対象が決まります。

人間が実際に確認したという状態とは別なので、単に入力欄へ移動しただけで確認が終わったのか分かりにくくなります。

推奨するのは、「未確認」「人間が確認済み」「修正済み」「未解決」の区別です。

修正した項目は確認済みにでき、何も変更せずに原本と一致していることを確認した場合にも、1タップで完了にできます。

### 3-8. AIによる複数レシートの連続確認を省力化する

現在、アップロード後にドキュメント一覧から対象を選んで確認する構成になっています。

複数枚をまとめて取り込む運用では、1枚を確定したら次の未確認レシートへ自動移動できるようにするべきです。

また、レシートに未確認の項目がなく、金額も一致し、重複の疑いがない場合は、確認作業を大幅に簡略化できます。

これは自動確定してよいという意味ではなく、確認するためのUIを軽量化するという意味です。

例えば、問題のないレシートは店名、日時、合計、品目数、決済元をコンパクトに表示し、詳細は必要な場合だけ展開する形にします。

## 4. 帳簿の編集・一括編集

### 4-1. 品目の負担割合を通常の編集画面から変更できない

重要度：高

[purchase-item-editor.tsx](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/ledger/ui/purchase-item-editor.tsx)

品目の編集フォームには、品名、カテゴリ、正規商品、金額、数量などがあります。

しかし、負担割合の編集欄はありません。

現在は、選択した品目をまとめて更新する機能に負担割合の変更がありますが、1品目の負担割合だけを変更する場合にも、選択操作と一括編集操作が必要になります。

これは不自然です。

新規購入・AI確認・既存帳簿で、同じ負担割合エディタを共通利用するべきです。

### 4-2. 品目単位表示から直接編集できない

重要度：中

[品目単位表示](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/ledger/ui/ledger-page.tsx#L318-L379)

品目単位表示では「購入を開く」ボタンがあり、購入単位表示へ切り替えて展開する構成です。

カテゴリや商品名を1つ修正したいだけなのに、表示モードの切り替えが必要になります。

品目単位表示でも、その場で編集可能な設計が適しています。

特にカテゴリと負担割合は、編集モードに入らなくてもクリックから直接変更できるようにすると便利です。

ただし、変更はすぐに視覚的に反映し、取り消し可能にします。ネットワーク処理待ちの間に操作をブロックしないことも重要です。

### 4-3. 複数品目を選択したとき、変更操作が大きすぎる

[ledger-item-bulk-actions.tsx](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/ledger/ui/ledger-item-bulk-actions.tsx#L25-L167)

一括編集パネルにはカテゴリ、負担割合、商品、タグなどの設定がまとめて表示されます。

しかし、ユーザーがカテゴリだけを変更したい場合には、他の設定は不要です。

選択後は「カテゴリ」「負担」「商品」「タグ」などの小さなアクションをまず表示し、選択した機能の入力欄だけを展開するほうが分かりやすいです。

4品目を選択中

操作対象を1つ選んだら、必要な設定だけ開きます。

複数の属性をまとめて編集したい場合には、連続して設定できます。

### 4-4. 商品選択で全商品を巨大なselectに並べない

[既存品目の商品選択](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/ledger/ui/purchase-item-editor.tsx#L42-L66)

ここでは商品カタログを`flatMap`して、すべてのバリエーションを`select`の選択肢にしています。

商品数が増えると、スクロールして探すことが非常に難しくなります。

既存の購入履歴から考えると、商品マスタは数百〜数千件に増える可能性があります。

この部分は検索可能なComboboxに変更し、現在の品名と店舗から候補を絞り込んで表示するべきです。

また、商品名を変更した場合には、正規化商品の候補も必要に応じて更新します。

### 4-5. 保存操作を完了したのかが分かりにくい

[saveItem](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/ledger/model/use-ledger-purchase-editor.ts#L131-L253)

品目の保存後には`refresh()`が呼ばれますが、編集セッション自体を終了させるわけではありません。

複数品目を順次編集する設計なら合理性はありますが、どの品目を保存済みで、どの品目に未保存の変更が残っているのかを分かりやすく表示する必要があります。

前述の購入単位の一括保存と合わせて、未保存・保存中・保存済み・競合を明確にするほうがよいです。

### 4-6. 検索欄とフィルタの情報密度が高い

[ledger-filters.tsx](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/ledger/ui/ledger-filters.tsx)

帳簿には、期間、カテゴリ、プール、決済元、タグ、入力元、原本の有無、金額など多数の検索条件があります。

機能面では十分ですが、普段の検索で常にすべての条件を見せる必要はありません。

最初は検索欄、期間、よく使う条件だけを表示し、詳細条件は「絞り込み」で展開する形がよいです。

適用中の条件はチップとして表示し、個別に解除できるようにします。

また、検索入力中は適切なデバウンスを設定してリクエスト数を抑えつつ、入力欄の反応自体は即時に保ちます。

## 5. 精算・送金の入力UX

### 5-1. 定期入金の記録で金額を自由に変更できない

重要度：高

[settlement-funding.ts:60–90](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/settlement/model/settlement-funding.ts#L60-L90)

定期入金の記録処理では、

```
const amountYen = line?.amountDueYen ?? 0;
```

として、必要入金額がそのまま使用されています。

つまり、「今回は予定の半分だけ入金したい」「多めに入金したい」といった操作を、この導線で行えません。

最初の要件でも、片方しか入金しないケースや、イレギュラーな入金があると説明されていました。

改善方法

入金の初期金額は計算された必要入金額にしつつ、自由に修正できるようにします。

精算画面には「予定どおり入金」と「金額を変更して入金」を用意するとよいです。

一部入金した場合は残額を繰り越し、過払いの場合も消去せず残高として管理します。

### 5-2. 入金元・入金先の口座を毎回選び直さない

[settlement-preview.tsx](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/settlement/ui/settlement-preview.tsx#L93-L170)

精算画面では各メンバーの入金元と入金先を選択できます。

これは必要な機能ですが、同じ銀行口座を毎月利用するなら毎回設定する必要はありません。

既存の選択状態保持の仕組みを活用し、明示設定したデフォルトや前回の入金元・入金先を優先してください。

また、普段は口座の選択欄を展開せず、「A銀行 → 共用銀行」のような要約表示にするのが適しています。

### 5-3. 送金種別の選択をもっと直感的にする

[settlement-transfer-form.tsx](https://github.com/walnuts1018/horse/blob/778cb41/web/src/pages/settlement/ui/settlement-transfer-form.tsx#L50-L161)

現在は「立て替え」「貸し借り」「贈与」をselectで選び、その後に貸主・借主・口座などを指定します。

家計簿に慣れていない利用者にとって、これらの違いを意識すること自体が少し難しい場合があります。

例えば入口を「誰かにお金を貸した」「お金をあげた」「立て替えた」といった行動ベースにするのがよいです。

必要なら、その操作が会計上どう扱われるかを短く表示します。

また、送金元を自分に、送金先を直近の相手にするなど、利用傾向に応じた初期値も効果的です。

## 7. 最終的に目指したい入力フロー

改善によって、日常的な操作がどれくらいシンプルになるべきかを整理します。

### 手入力

1品目の買い物

目標

1. 品名を入力
2. 金額を入力
3. 保存

店名・決済元・カテゴリ・負担割合は履歴と設定から補完。必要な場合だけ変更する。

複数品目の買い物

目標

品名 → 金額 → 次の品名、を連続して繰り返す。最後は保存するだけ。

途中でカテゴリや負担割合を変更したくなっても、別画面へ遷移せずその場で変更できる。

### AI取り込み

通常のレシート

目標

1. 撮影する
2. 画像を確認して取り込む
3. 認識結果を確認して確定

認識に誤りがあるレシート

同じ画面で間違った品目だけを直し、必要なら負担割合も編集してから確定する。原本との往復は不要。

このように、正常系では不要な画面や確認を増やさず、例外が発生したときだけ必要な操作を表示する設計が理想です。

## 8. 実装優先順位

今回見つけた改善点を、効果とリスクで整理すると次の順番を推奨します。

| P0 | カテゴリ選択の状態不整合を修正 | 誤登録を防ぐ |
| P0 | AI金額修正のスコープを品目単位にする | ほかの品目への影響を防ぐ |
| P0 | 連続入力中の自動遷移を防止 | 入力の中断を防ぐ |
| P0 | 貼り付け時のカンマ解析修正 | 金額の誤登録を防ぐ |
| P0 | IME・空欄Enterの操作を修正 | 予期しない操作を防ぐ |
| P1 | AI確認画面で品目・負担割合を完全編集可能にする | 編集画面の往復をなくす |
| P1 | 既存購入をまとめて保存可能にする | 複数品目の修正を高速化 |
| P1 | 撮影後のアップロード自動化 | 確認操作を減らす |
| P1 | 負担割合のクイック選択 | 日常操作を減らす |
| P1 | 新規購入で品目の一括編集を可能にする | 複数品目の修正を高速化 |

### 実装時に追加してほしいUXテスト

改善した結果を確実に検証できるよう、PlaywrightによるE2Eテストを追加するとよいです。

テストするべきなのは単なるフォーム送信成功だけではありません。

例えば、スマホの画面幅で10品目を連続入力できること、IME変換中の矢印キーやEnterで誤操作が起きないこと、レシートの1品目の修正がほかの品目に影響しないこと、購入を連続登録しても画面遷移で入力が中断されないことなどです。

また、操作数を測定するテストシナリオを用意します。

| シナリオ | 目標 |
| ----------- | ------------------ |
| 1品目の新規購入 | 品名・金額・保存で完結 |
| 10品目の連続入力 | 品目ごとの画面遷移なし |
| 5品目の負担割合変更 | 1回の一括操作 |
| AIの金額1件訂正 | 対象行だけ修正して確定 |
| 20品目中3品目を訂正 | 個別保存3回を不要にする |
| レシートを5枚取り込み | アップロード操作を枚数分繰り返さない |

## 総評

現状のhorseは、基本的な高速入力の仕組みはかなり用意されていますが、複数品目の例外的な修正をすると急に手数が増えるという傾向があります。

特に目立つのは次の3つです。

第一に、購入入力・AI確認・帳簿編集で品目エディタが分かれていること。 これによって、画面ごとに変更できる項目や操作方法が異なっています。可能な限り同じ品目編集モデルとUIコンポーネントを共有することで、ユーザーが覚える操作を減らせます。

第二に、標準的な入力は簡単でも、負担割合の変更や複数品目の訂正が重いこと。 普段の入力で使う機能ほど、1タップで完了するプリセットや一括編集を重視するべきです。

第三に、AI取り込みが通常の手入力と同じ自由度を持っていないこと。 AIはあくまで入力を代行する手段であり、AIが作成した候補も通常の購入と同じように編集できるべきです。

私なら、まず 「新規購入・AI確認・既存帳簿で共通利用できる品目エディタ」 を中心に再構成します。商品名、金額、カテゴリ、負担割合、証拠との対応、複数選択、Undoを共通化し、入力元によって必要な情報だけ表示する方式です。

そのうえで、連続入力中の遷移、フォーカス、カテゴリ選択、コピー、保存操作といった細部を直すのが、最も大きなUX改善につながると思います。
