# Horse フロントエンド UXレビュー

対象：[walnuts1018/horse](https://github.com/walnuts1018/horse) の `main`、commit [`e247076a`](https://github.com/walnuts1018/horse/commit/e247076a8bc26b0380641f549a7ad016baf07874)（2026年10月13日）。

今回はReactの書き方よりも、実際の操作でストレスが生じる箇所、誤ったデータを保存・表示する箇所、モバイルで使いづらい箇所を重視しました。

まだ実ブラウザでの操作テストは行っていないため、以下はソースコードを根拠にしたレビューです。見た目やタッチ操作の最終評価には実機検証が必要ですが、コードだけでも修正すべき問題がかなり見つかっています。

## P1：日常利用で大きな不満につながる問題

### 7. AI取り込みの確定画面では、複数決済とカテゴリ確認が弱い

[imports-page.tsx: confirm](https://github.com/walnuts1018/horse/blob/e247076a8bc26b0380641f549a7ad016baf07874/web/src/pages/imports/ui/imports-page.tsx#L577-L669)

AIの解析結果には複数の決済手段を持たせられますが、確認処理では単一の`paymentAccountId`を選び、購入総額を全額その口座へ割り当てています。

例えば、3,000円の会計で現金1,000円＋クレジットカード2,000円を使った場合、確認画面ではその分割を十分に表現できません。

また、AIから確定する各品目には`categoryId`や`productVariantId`を渡していません。購入後に帳簿で分類し直す必要があるケースが増えます。

ここはレシートの解析結果を直接確認できる画面なので、品目の修正、カテゴリ、負担先、決済内訳を確定前に一通り編集できることが望ましいです。

毎回すべてを手入力するのではなく、商品マスタ・過去の購入・ルールによって自動入力したうえで、不確実な項目だけを強調してください。

### 10. モバイルUIの文字が小さすぎる

[global.css: モバイルスタイル](https://github.com/walnuts1018/horse/blob/e247076a8bc26b0380641f549a7ad016baf07874/web/src/app/styles/global.css#L3148-L3927)

これはデザイン面で最も優先して改善したい点です。

現在のモバイルCSSには、非常に小さな文字サイズが多数指定されています。

| 要素 | 現在の設定例 |
| --------- | ------ |
| グラフの金額ラベル | 7px |
| 分析サマリーの補足 | 7px |
| 購入入力の保存状態 | 8px |
| ボトムナビの文字 | 8px |
| 購入入力欄 | 10px |
| 一部の操作ボタン | 9px |

特に購入入力欄が10pxというのは厳しいです。

iOS Safariでは小さい入力文字サイズが自動ズームの原因になることもあり、連続入力の体験に悪影響を与えます。

推奨する方向性は、スマホの重要な本文・入力欄を少なくとも14〜16px程度で設計し、入力欄は16pxを基本とすることです。

一方、グラフ内の小さい数字をすべて大きくすると収まらなくなります。そこは金額を常時すべて表示する設計を見直し、選択した日だけ詳細を表示する形にするのがよいです。

### 11. タップ対象が小さい

同じCSSでは、操作ボタンや入力欄の高さが30〜35px程度になっている箇所が多数あります。

一例として、

- 決済内訳の削除ボタンは25px幅
- 入力欄は34px高
- 品目追加ボタンは31px高
- 購入確定ボタンは35px高

となっています。

密度の高いデスクトップUIでは許容されても、スマートフォンでの誤タップが増えます。

改善案： タッチ環境では、主要な操作対象の実効タップ領域を44px前後に確保してください。アイコン自体を大きくする必要はなく、透明なヒット領域を広げても構いません。

また、画面幅380px以下では「元に戻す」の文字を消してアイコンだけにしています。ここは意味が分かるARIAラベルも必要です。

### 12. 毎日の品目入力までにスクロールが必要

現在の購入追加画面は、おおむね次の順序です。

店名・日時・決済内訳

前回の購入・よく使う店

品名と金額の入力

毎日の利用では、買ったものを追加する作業が最も多いはずです。

しかしスマホでは、その入力欄がページの下方に配置されます。過去履歴が増えると、入力開始までのスクロール量も増えます。

私なら次の順序へ変更します。

品名・金額・品目追加

よく使う品目・前回の購入

店名・日時・決済元（コンパクト表示）

合計・保存

また、スマートフォンの`+`ボタンを押した場合、手入力とレシート撮影の2つを自然に選べるようにしたいです。

撮影が多い家庭なら、ボトムナビの中央ボタンから直接カメラを開ける導線にも価値があります。

### 13. 下書きの保存状態表示が実際の状態と一致しない

[下書きの自動保存](https://github.com/walnuts1018/horse/blob/e247076a8bc26b0380641f549a7ad016baf07874/web/src/pages/purchase-create/ui/purchase-create-page.tsx#L178-L220)、[保存状態の表示](https://github.com/walnuts1018/horse/blob/e247076a8bc26b0380641f549a7ad016baf07874/web/src/pages/purchase-create/ui/purchase-create-page.tsx#L620-L634)

`hasUnsavedChanges`は編集時にtrueになりますが、「下書き保存済み」という表示は基本的に`savedAt`の有無で判定しています。

一度保存した後に新しい変更を加えても、`savedAt`はそのまま残るため、次の保存が完了するまで「保存済み」と表示されます。

内部では離脱防止に`hasUnsavedChanges`を使っているので、状態が完全に一致していません。

改善案： 保存状態を`editing / saving / saved / failed`のように明示的な状態機械として管理し、編集中は必ず「保存中」または「未保存の変更あり」と表示します。

保存エラー時は、ただテキストを表示するだけでなく、再試行ボタンと編集中のデータが残っていることを明確に伝えると安心です。

### 14. 取り込み画面のカメラ導線を分けたい

[imports-page.tsx: file input](https://github.com/walnuts1018/horse/blob/e247076a8bc26b0380641f549a7ad016baf07874/web/src/pages/imports/ui/imports-page.tsx#L727-L752)

ファイル入力に`capture="environment"`と`multiple`が両方指定されています。

デバイスやブラウザによって、カメラ撮影・写真ライブラリ・ファイル選択の選択肢が異なり、意図どおりの操作にならない可能性があります。

特にレシートは1枚ずつ連続撮影したいことが多いので、次の2つは明示的に分けた方がよいです。

- 「レシートを撮影」：背面カメラを優先
- 「画像・PDF・明細を選ぶ」：複数ファイル選択

加えて、撮影した写真をその場で確認し、回転・トリミングしてから送信できると、AI解析の再試行も減らせます。

## P2：情報設計と画面の分かりやすさ

### 15. 設定画面に日常的な業務が集まりすぎている

[settings-page.tsx](https://github.com/walnuts1018/horse/blob/e247076a8bc26b0380641f549a7ad016baf07874/web/src/pages/settings/ui/settings-page.tsx#L1087-L2398)

現在の設定画面には、マネープール、残高、決済元、カテゴリ、標準負担、優先ルール、商品マスタ、招待、タグ、予算、定期支出、資金移動、メンバーなどがまとめられています。

これらは性質がかなり異なります。

例えば、予算管理や口座間移動は「アプリの設定」ではなく、日常的な家計操作です。

すべてを設定の中に置くと、目的の機能を探しづらくなります。

おすすめは次の分類です。

| 場所      | 含める機能                       |
| ------- | --------------------------- |
| 帳簿      | 購入、返品、訂正、照合                 |
| 精算・資金移動 | 入金、貸付、返済、口座間移動              |
| 分析・予算   | 支出分析、月次予算、定期支出              |
| 設定      | 家庭、メンバー、口座、負担ルール、カテゴリ、商品マスタ |

これはすべてを別のトップレベルページに分けるという意味ではありません。設定内もタブやサブルートに分け、必要な情報だけを表示するのがよいです。

### 16. 帳簿検索のサーバー側絞り込みがない

帳簿の検索語、期間、カテゴリ、タグ、決済元などの条件はURLの検索パラメーターへ保存し、共有URLから再現できます。

検索処理は取得済みの購入履歴をブラウザで絞る方式です。データが増えると全ページ読み込みが発生するため、検索条件のうち主要なものをサーバー側へ移す必要があります。

### 17. エラーメッセージと成功メッセージの表現が混在している

[horse-app.tsx: Toast](https://github.com/walnuts1018/horse/blob/e247076a8bc26b0380641f549a7ad016baf07874/web/src/app/horse-app.tsx#L617-L627)

`showNotice`は成功と失敗の両方に使われていますが、表示されるToastには常にチェックアイコンが付いています。

つまり、ログアウト失敗などのエラーメッセージも、見た目上は成功通知になります。

通知を`success / error / warning / info`の状態に分け、それぞれに適切なアイコンとアクセシビリティ属性を使用した方がよいです。

また、エラーには可能な限り「再試行」「入力内容を修正」「詳細を見る」といった次の操作を用意してください。

### 18. AIレビューは原本と修正欄を並べて確認したい

現状の取り込み画面では、原本プレビュー、認識された品目、税計算候補、照合情報が長いページ内に配置されています。

レシートのOCRを確認する場合、ユーザーは原本と入力欄を何度も見比べます。

デスクトップでは左側に原本、右側に品目と金額の編集欄を配置し、原本側を固定できるようにすると作業効率が上がります。

スマホでは原本を折りたたみ可能な上部プレビューまたはボトムシートで表示し、品目をタップすると対応する原本位置へ移動する方式が向いています。

特に改善したいのは、「全項目を読み直す」のではなく、AIが自信を持てなかった項目と整合しない金額だけを順番に確認するレビュー体験です。

## P3：アクセシビリティと一貫性

### 19. キーボード・スクリーンリーダー向けの情報が不足している

CSSに`:focus-visible`があり、フォームにもARIAラベルがかなり追加されている点はよいです。

ただし、改善できるところがあります。

たとえばホームの7日間グラフは棒の高さで金額を表していますが、各日付・金額をスクリーンリーダーが読み取れる代替表現がありません。

ナビゲーションにも`button`を使用しているため、一般的なリンクの「新しいタブで開く」といった操作ができません。TanStack Routerの`Link`を利用する方が自然です。

また、薄いグレーの補足文字と7〜9pxの文字は、コントラストや可読性の観点からも検証が必要です。

### 20. 初回セットアップの導線が弱い

現在、家庭を新規作成したあと、購入を記録するには決済元や負担ルールなどの設定が必要です。

しかし、利用者はそれぞれの設定をどの順序で行えばよいか判断しなければなりません。

例えば「設定で決済元を登録してください」というメッセージを出すだけでなく、必要な設定画面へ直接遷移できるとよいです。

初回だけ、次のようなセットアップガイドを表示するのが適切です。

### 家計簿の初期設定

家庭を作成

完了

負担先を設定

決済元を登録

標準の負担割合を決める

最初の買い物を記録

これはオンボーディングのために複雑なツアーを作る必要はなく、設定の完了状況を検出して、未設定部分へのリンクを出すだけでも実現できます。

## 最後に：UXの回帰テストを導入すべき

現状、フロントエンドにはRelay生成物検証、TypeScript、Oxlint、Stylelint、Steigerなどが用意されています。しかし、リポジトリのフロントエンドにはPlaywrightなどによる実操作のE2Eテストが見当たりません。

UX改善を重ねるなら、Playwright + axe-coreによるブラウザテストを導入することを推奨します。

とくに以下の操作は必須の回帰テストにしたいです。

1. ネットワークが切れた状態で購入を保存し、復帰後に一度だけ登録される。
2. 同じ入金・送金を再試行しても二重記録されない。
3. ブラウザの戻る・進む・再読み込みで家庭と検索条件が維持される。
4. 320px、375px、430px程度のスマホ画面で、購入・取り込み・精算操作が横スクロールなしで完了できる。
5. キーボードのみで商品検索・品目追加・負担割合変更・確定まで操作できる。

テスト用のブラウザはChromiumだけでなく、WebKitとモバイルのビューポートを含めるとよいです。Android Chromeと実機Safariの操作検証は別途実施する価値があります。

## 総合評価

Horseは、機能の種類としては非常に充実してきています。購入履歴コピー、キーボードでの品目移動、オフラインOutbox、複数決済、AIの税計算候補、原本の位置表示、衝突時の再適用など、日常利用を考えた機能がすでに存在します。

ただ、現時点では多機能さに対して、操作の一貫性と分かりやすさが追いついていないと感じます。

特に改善効果が大きいのは、次の3つです。

第一に、入力・確認した内容が失われないことです。取込画面では編集内容を解析結果の更新から保護しましたが、他のフォームやタブ終了時の状態保持は引き続き確認が必要です。

第二に、数字が常に正しい範囲のデータを示すことです。ホームのグラフと分析途中の部分集計は、家計簿への信頼性に直結します。

第三に、スマホで日々の操作を少ないタップ・スクロールで完了できること。 現状の7〜10pxの文字と小さなボタン、品目入力までの長い導線は、かなり改善余地があります。

次に大きな機能を足すよりも、まずこれらを修正し、手入力なら数秒で登録、レシートなら不確実な箇所だけを確認して確定できる体験へ仕上げるのが、Horse全体の使い心地を高めるうえで最も効果的だと思います。
