# Horseの追加レビュー

## SubscriptionのDB polling

購入イベントと共有下書きはHousehold単位の共有pollerで検索し、購読数に比例するDB queryを避けている。PostgreSQLのquery tracerを使ったfocused integration testでは、異なるHouseholdの50購読を購入イベント検索1回に、異なるdraftの50購読をdraft検索1回にまとめた。実イベントを含む別の試験では、100件のイベント境界後に同じ購入の更新イベント2件を1回のpollで取得し、2購読へcursor順に配信した。2イベントの取得と購入hydrateは合計12 queryで、hydrate query数はイベント1件時と同じ11回だった。ローカルの試験用PostgreSQLでは、空の1回の検索にかかった時間は購入イベントが約1.7ms、共有下書きが約1.0msだった。

購読数が同じHouseholdまたはdraftに集中する場合は検索条件を共有し、購読者数に比例してpoll queryやDB接続を増やさない。異なるHouseholdやdraftのcursorは1 queryあたり16,000件に分割し、1 queryのbind parameter数を32,000以下に保つ。16,001件をPostgreSQLへ問い合わせるintegration testでは、purchase/draftの両pollが2 queryに分割され、全queryが成功することを確認している。16,001件の分割で全cursorが重複・欠落なく上限内のchunkに入ることをunit testで確認している。purchaseイベントはchunkごとの結果をcursor順に統合し、全chunk合計で最大100件を既存の配信処理へ渡す。購入イベントを取得すると変更対象の購入情報を追加検索するため、イベント数が多い場合のquery数と応答時間は購読query数だけでは評価できない。

購読channelが満杯の場合、未配信イベントを毎秒検索し直していたため、配信に成功したかどうかをpollerの待機間隔へ反映した。満杯のchannelだけが残る場合はidle時の指数backoffを使い、最大5秒間隔で再試行する。購入イベントを一度に100件取得しても、配信がなければ即時pollを続けない。変更対象の購入情報はイベントごとではなく、poll内の購入イベントをまとめて取得する。上記の2イベント試験では、購入hydrateのquery数がイベント数に比例して増えないことも確認した。

kurumiのHorse DBへport-forwardし、異なるHouseholdとdraftのランダムUUIDを各50個使う既存integration testを2回実行した。各pollは1 queryを実行し、所要時間は購入イベント検索が約48.7〜54.2ms、共有下書き検索が約46.6〜50.1msだった。応答行のない検索で、所要時間にはクラスターまでのport-forward遅延が含まれる。実データのイベント量や購読中のHousehold数、複数異なる購入に対する実データ量での実行計画、同時接続時の負荷は測定していない。

確認時点では`horse-api`は1 replica、Horse DBの接続は6本で、PostgreSQLクラスターは3 instanceで正常だった。pollerは購入イベントと共有下書きを直列に検索し、DB接続を占有するのは各queryの実行中だけである。この一点観測とUUID検索だけでは、同時購読数が増えた場合のBob DSLのOR条件の実行計画、購読query以外のDB接続との競合、購入イベントが多い状態での追加query負荷を評価できないため、項目は未解決として残す。
