# Horse UI/UXレビュー — 操作数の最小化を基準に

対象：[walnuts1018/horse](https://github.com/walnuts1018/horse) の `main` ブランチ、2026年10月14日時点。

結論として、当初の目標にかなり近づいていますが、まだ「最小操作で迷わず使えるUI」とは言い切れません。 とくに、日常的な買い物登録とAIレシート確認には、操作数や確認負荷をさらに減らせる箇所があります。

既存の `docs/reviews`、`docs/decisions/review-responses.md` も確認しています。すでに対応された機能を未実装扱いせず、新しく確認できた問題を優先します。

今回のレビューはGitHub上の実装に対する静的レビューです。ブラウザでの実操作、タップ数計測、実機のキーボード挙動までは検証していないので、その点は区別します。

## 1. 最初に見つかった重要な改善点

### P1：最後に入力中の品目が、画面の合計額に含まれない

該当箇所：

- [purchase-create-page.tsx L131–132](https://github.com/walnuts1018/horse/blob/main/web/src/pages/purchase-create/ui/purchase-create-page.tsx#L131-L132)
- [purchase-create-page.tsx L322–347](https://github.com/walnuts1018/horse/blob/main/web/src/pages/purchase-create/ui/purchase-create-page.tsx#L322-L347)

現在、合計金額の算出対象は `itemsValue.items` のみです。

一方で、「保存して送信」を押すと、入力欄に残っている未追加の品目も `prepareForSubmit()` によって保存対象に含まれます。

例えば次の状況です。

| 状態 | 金額 |
| ---------- | ---- |
| 追加済み：牛乳 | ¥200 |
| 追加済み：パン | ¥150 |
| 入力中：ヨーグルト | ¥180 |
| 画面に表示される合計 | ¥350 |
| 実際の保存対象の合計 | ¥530 |

つまり、表示されている合計と、保存操作の結果が一致しない時間が存在します。

これは単に金額表示の問題ではなく、ユーザーが最後の品目の追加を忘れたのか、すでに追加したのか判断しづらくなる問題です。

改善案： 入力中の品目の金額も合計プレビューへ含め、未確定分を区別します。保存時には今表示している合計と同じ計算結果を使います。

決済金額の自動調整も同じプレビュー合計に連動させることで、入力中だけ金額がずれる状態をなくせます。

### P1：AIレシート確認で品目リストが二重に表示される

該当箇所：

- [receipt-review.tsx L356–403](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/ui/receipt-review.tsx#L356-L403)
- [receipt-review.tsx L573–613](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/ui/receipt-review.tsx#L573-L613)

現在は、レシート概要に全品目の一覧があり、その下の編集エリアでも品目を列挙しています。

編集エリアが開いている状態では、例えば20品目のレシートなら、実質的に20行の概要と20行の編集項目が並びます。

画像と照らし合わせて修正したい利用者にとって、これは画面が長くなりすぎます。

改善案： 品目一覧は原則1つに統合します。

一覧の行をタップすればその場で編集でき、対応する原本画像の領域も連動する形がよいです。概要は店名、日時、合計、品目数、確認が必要な件数程度に絞ります。

特にスマホでは、問題のある品目へ到達するまでのスクロール量を大きく削減できます。

### P0：精算画面の「次回の入金」が、正負の金額を相殺してしまう

該当箇所：

- [home-page.tsx L106–107](https://github.com/walnuts1018/horse/blob/main/web/src/pages/home/ui/home-page.tsx#L106-L107)
- [settlement-view.ts L3–5](https://github.com/walnuts1018/horse/blob/main/web/src/pages/settlement/model/settlement-view.ts#L3-L5)
- [settlement-preview.tsx L53–57](https://github.com/walnuts1018/horse/blob/main/web/src/pages/settlement/ui/settlement-preview.tsx#L53-L57)

現在、「次回の入金」として表示される合計は、各メンバーの `amountDueYen` を符号付きのまま合計しています。

例えば、Aの必要入金額が5,000円、Bの過払い・控除残高が−5,000円なら、トップに表示される金額は0円です。

しかし、Aにはまだ5,000円の入金義務があります。 画面上の「入金0円」は、利用者に誤った印象を与えます。

改善するには、少なくとも次の値を分離して表示します。

- 入金が必要な金額：正の必要額の合計
- 過払い・控除残高：負の必要額の絶対値の合計
- 差引残高：必要なら内訳内に表示

ホームでは「次回入金 ¥5,000」を主表示し、Bの過払い5,000円は補助情報にするのがよいです。精算画面では、誰が実際に何をすべきかを最優先で示します。

### P0：共用プールが複数ある場合、選択した入金先と記録対象のプールが一致しない

該当箇所：

- [settlement-funding.ts L112–132](https://github.com/walnuts1018/horse/blob/main/web/src/pages/settlement/model/settlement-funding.ts#L112-L132)
- [settlement-preview.tsx L77–105](https://github.com/walnuts1018/horse/blob/main/web/src/pages/settlement/ui/settlement-preview.tsx#L77-L105)

入金先のセレクトでは、複数の共用プールに属する銀行口座を選択できます。

ところが、入金登録時の `poolId` は選択した入金先から求めず、`household.pools.find(...)` で最初に見つかった共用プールのIDを使っています。

バックエンドには、入金先口座が指定されたプールに属することを確認する処理があるため、2つ目の共用プールの口座を選ぶと登録が拒否される可能性が高いです。

これは操作数の問題以前に、当初要件の「複数プール」を扱う画面として修正が必要です。

改善案： 精算・入金を対象プールごとに表示し、そのプールに属する入金先だけを候補にします。Mutationに渡す`poolId`は選択中の精算対象プールと一致させ、別プールへの入金を暗黙に混在させません。

### P1：商品候補が出ると、Enterによる最短入力が途切れる可能性がある

該当箇所：

- [purchase-item-entry.tsx L108–146](https://github.com/walnuts1018/horse/blob/main/web/src/pages/purchase-create/ui/purchase-item-entry.tsx#L108-L146)
- [edit-purchase-items.tsx L465–483](https://github.com/walnuts1018/horse/blob/main/web/src/pages/purchase-create/ui/edit-purchase-items.tsx#L465-L483)

品名入力のComboboxは`autoHighlight`を有効にしています。一方、「Enterで金額入力へ進む」処理には、`aria-activedescendant`が存在しないことという条件があります。

つまり、候補が表示されて最初の項目が自動選択状態になっていると、Enterは金額欄への移動ではなく、候補の選択に消費される可能性があります。

これは「品名 → Enter → 金額 → Enter → 次の品名」という、最も重要な連続入力導線に影響します。

改善案： 候補の自動ハイライトと、ユーザーが矢印キーなどで明示的に候補を選択した状態を区別することです。通常のEnterは金額欄へ進み、明示的に候補を選んでいる場合だけ候補確定に使います。

候補を選ぶことが任意の補助機能であり、候補が出現したことで通常入力の操作数が増えない設計にします。

### P1：決済元検索で日本語IMEのEnterが候補選択と衝突する

該当箇所：[edit-purchase-payments.tsx L49–88](https://github.com/walnuts1018/horse/blob/main/web/src/pages/purchase-create/ui/edit-purchase-payments.tsx#L49-L88)

決済元の検索欄では、Enterを押すと候補を選択する処理がありますが、日本語IMEの変換中かどうかを確認していません。

例えば「楽天銀行」と入力するとき、変換確定のEnterが決済元候補の選択として扱われる危険があります。

品名入力ではすでにIMEを考慮しているため、決済元検索にも同じ原則を適用します。変換中はEnter、矢印キー、EscapeによるCombobox操作を発生させないようにしてください。

## 2. スマートフォンの操作導線

### P1：AIレシート確認で、原本画像の表示が編集より先に来る

該当箇所：

- [imports-page.module.css L439–470](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/ui/imports-page.module.css#L439-L470)
- [evidence-source-preview.tsx L90–133](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/ui/evidence-source-preview.tsx#L90-L133)
- [evidence-source-preview.tsx L194–244](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/ui/evidence-source-preview.tsx#L194-L244)

900px未満では「原本 → 編集」の縦並びになります。しかも原本表示の`details`は初期状態で開いています。

さらに原本側には、範囲の再抽出、品目の選択ボタン、OCR行の一覧などもあります。

これは画像の検証機能としては充実していますが、通常の確認操作に必要な情報よりも、解析・再抽出の専門的なUIが先に来ています。

特に長いレシートの場合、編集したい品目までスクロールする負担が大きくなります。

改善案

スマホでは、原本全体を常時展開するのではなく、現在確認中の品目に対応する画像の一部を編集欄の近くに表示します。

原本全体は1タップで拡大できるようにし、再抽出・OCR行・座標調整は必要なときだけ展開します。

PCでは既存の2ペイン構造を活かします。

この変更は、単なる見た目の改善ではなく、原本と入力欄の間を行き来するスクロール数を削減するためのものです。

### P1：前回の買い物をコピーした後、コピー内容が画面外になる

該当箇所：

- [purchase-create-page.module.css L233–245](https://github.com/walnuts1018/horse/blob/main/web/src/pages/purchase-create/ui/purchase-create-page.module.css#L233-L245)
- [edit-purchase-details.tsx L152–197](https://github.com/walnuts1018/horse/blob/main/web/src/pages/purchase-create/ui/edit-purchase-details.tsx#L152-L197)

モバイルでは、画面が次の順番です。

`購入情報 → 品目入力・品目一覧 → 過去の購入履歴`

「前回の購入をコピー」は過去の購入履歴にあります。

ところが、コピーした品目はその上にある品目一覧へ反映されます。コピー処理自体には、コピー先の品目へスクロール・フォーカスする操作がありません。

ユーザーはコピーした後、内容を確認するために上へ戻る必要があります。

おすすめは、過去の購入からコピーする操作を品目入力の近くにも配置することです。あるいはコピー完了直後に品目一覧へ移動し、最初の編集対象を表示します。

また、現在のコピー処理は既存の入力品目を置き換えます。入力済み品目が存在する場合は、「置換」「追加」を選べるようにすると、間違った操作からの復旧も簡単になります。

### P1：レシートの「一致を確認」の後、次の確認対象へ移動しない

該当箇所：

- [receipt-review.tsx L644–669](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/ui/receipt-review.tsx#L644-L669)
- [use-import-confirmation.ts L348–413](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/model/use-import-confirmation.ts#L348-L413)

確認対象を順番に案内する仕組みはあります。しかし、品目の「一致を確認」を押した後、その操作自体では次の品目へフォーカスを移しません。

確認対象が更新されると次の品目がアクティブになり得ますが、フォーカスが品目内に残っていると自動スクロールしない条件も存在します。

そのため、連続して10品目を確認する際には、余分なスクロールや「次へ」操作が必要になる可能性があります。

改善案： 「一致を確認」を押したら、次の要確認項目へ自動的に進み、その原本部分を表示します。

もちろん、ユーザーが任意の品目を編集中であれば勝手に移動させません。「順番に確認しているとき」に限った動作にします。

## 3. 帳簿の編集・一括変更

### P1：品目金額を変更したとき、決済差額の表示が古い購入合計に基づく

該当箇所：

- [purchase-edit-form.tsx L133–142](https://github.com/walnuts1018/horse/blob/main/web/src/pages/ledger/ui/purchase-edit-form.tsx#L133-L142)
- [use-ledger-purchase-editor.ts L300–326](https://github.com/walnuts1018/horse/blob/main/web/src/pages/ledger/model/use-ledger-purchase-editor.ts#L300-L326)

購入編集フォームの差額表示は、保存済みの`purchase.totalYen`を使っています。

しかし、同じ編集セッションで品目金額を変更できるため、編集中の品目合計と保存済み購入合計が異なる場合があります。

例として、100円の商品を120円に修正したのに、決済額が100円のままであれば、本来は20円の差額を認識する必要があります。

改善案： 購入作成、帳簿編集、レシート確認で、それぞれ異なる計算方式を持たせるのではなく、編集中の品目金額と決済内訳から導出されるプレビューモデルを共通化します。

画面に表示する合計、差額、保存可否が、必ず同じデータを参照するようにします。

### P1：一括商品変更が、商品数の増加に弱い

該当箇所：[ledger-item-bulk-actions.tsx L144–194](https://github.com/walnuts1018/horse/blob/main/web/src/pages/ledger/ui/ledger-item-bulk-actions.tsx#L144-L194)

一括編集の「商品」は、すべての商品バリエーションを列挙する通常の`select`です。

商品マスタが数百〜数千件になると、目的の商品を見つける操作が大変になります。

一方、通常の商品編集では検索可能な商品選択UIがすでに存在しています。

一括編集でも同じ検索基盤を利用し、品名・別名・型番・容量で探せるようにするべきです。

また、一括タグ編集にはネイティブの`select multiple`が使われています。スマホでは選択状態が分かりづらく、複数選択の方法もOSによって異なります。

こちらはチェック付き候補一覧へ変更し、「選択中のタグ」をチップで見せる方式が適切です。

## 5. 既存レビューで指摘されていることと、すでに改善されたこと

既存の `docs/reviews/uiux.md` には、帳簿の通常編集に明示的な編集開始・保存操作が必要な点と、同じ未確定購入の共有編集がフロントエンドに結び付いていない点が記載されています。

後者については、現在のリポジトリには `sharedPurchaseDraft` のGraphQL Query/Mutation/Subscriptionおよびバックエンドの実装が存在します。一方、新規購入画面は依然としてローカルの下書きを中心に操作しています。したがって、「バックエンド機能がまったくない」のではなく、用意された共有下書き機能を入力UXへ統合することが残っていると整理するのが正確です。

逆に、既存レビューに残っている「決済元候補を検索できない」という指摘は、現行コードには検索入力が実装されているため、そのまま再指摘すべきではありません。

また、以下は現行実装で確認できた長所です。

- 品名・金額の連続入力と日本語IMEを考慮した品名欄
- CSV/TSVの複数行貼り付け
- 商品候補、過去カテゴリ、前回価格の利用
- 店舗別の決済元記憶
- 品目の負担割合変更と一括編集
- 購入作成中のUndo/Redo
- オフライン送信待ちと再送
- AIレシートの画像領域との対応付け
- AI確認内容・手動訂正の下書き保存
- 複数の税計算候補と金額差の表示
- 取り込み後の次のレシートへの移動

これらを作り直す必要はありません。今の実装を土台に、より短い操作経路にするべきです。

## 6. 最も重要な改善順序

今回の新規指摘を、作業順にまとめると次のようになります。

| 順位 | 改善 | 理由 |
| -- | ------------------------ | ------------------- |
| 1 | 精算合計の正負分離と共用プールの入金先整合 | 金銭的に誤解を招く表示・操作失敗を防ぐ |
| 2 | 購入入力中の合計と保存対象を一致させる | 日常入力の信頼性に直結 |
| 3 | 商品候補・IMEのEnter操作を修正 | 最重要の連続入力を妨げない |
| 4 | スマホのAI確認画面を単一品目リスト中心に再構成 | スクロールと視線移動を削減 |
| 5 | AI確認後の次項目への自動移動 | 修正・確認の連続操作を短縮 |
| 6 | 購入コピーと店名変更の導線を短縮 | 手入力の余分な画面移動を削減 |
| 7 | 帳簿編集の合計・差額プレビュー統一 | 編集時の誤解と手戻りを防止 |
| 8 | 商品・タグの一括選択UIを検索可能にする | 商品数が増えても操作数を抑える |

## 7. 完成度を判断するには、操作数を自動計測するべき

最終的に「完璧なUI/UX」へ近づけるには、実装されている機能数よりも、代表的な操作を何手で完了できるかを評価したいです。

例えば、次のようなE2Eテストを設けます。

| 操作シナリオ | 目標とする体験 |
| ------------- | ----------------------------- |
| 同じ店で商品3個を入力 | 店名・日時・決済元は再入力不要。商品名と金額の連続入力だけ |
| レシート20品目、誤りなし | 原本・金額・決済元を確認して1回で確定 |
| レシート20品目、誤り2件 | 誤った2箇所だけ変更し、確定 |
| 10品目の負担を一括変更 | 対象を選択し、負担ルールを1回指定 |
| 過去の買い物をコピー | コピー直後に編集する品目が視界に入る |
| 帳簿の品名を1文字修正 | 編集開始・修正・保存まで余計な画面遷移なし |

各シナリオについて、スマホとPCを分けて、タップ数、キーボード切替回数、スクロール距離、完了時間、誤操作を計測します。

特にReactのコンポーネントテストでは見えにくい、ソフトウェアキーボードが開いた際のレイアウト移動や、候補が出たときのEnterの挙動をPlaywrightのブラウザテストと実機検証で確認するべきです。

## 総評

Horseは当初の構想を表面的に実装した段階ではなく、内部的にも複雑な要件をかなり具体化しています。特に購入入力・AI確認・会計の整合性を意識した実装は評価できます。

ただし、UXを改善する余地はまだ明確にあります。

最も目立つのは、機能を追加するたびに、利用者が目にする項目や操作場所も増えていることです。

レシートの原本確認、税候補、OCR行、品目編集、負担割合、決済元はすべて必要な機能です。しかし、それらを常に画面に並べる必要はありません。

理想的には、普段の入力では商品名と金額だけが中心にあり、AIが正しく入力できた場合は確認だけで済み、誤りがあった場合はその部分に直接移動できます。

次の改善では、新機能の追加よりも、すでにある機能を何回の操作で使えるか、そして何を表示しなくても困らないかを徹底して見直すことが最も効果的です。

今回のレビューはソースコードの静的確認に基づいているため、実際の画面で操作数・速度を測定した完成度判定ではありません。それでも、上記の改善点は具体的なコードから根拠を確認できたものです。
