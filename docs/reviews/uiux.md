# Horse UI/UXレビュー — 操作数の最小化を基準に再評価

対象： [walnuts1018/horse](https://github.com/walnuts1018/horse) 確認コミット： [`ddf443e`](https://github.com/walnuts1018/horse/commit/ddf443e7229082aea19ac90dee2e8022cba33acd)（2026年10月14日）

## 総評

現状はかなり多くの便利な機能が実装されていますが、当初の目標である「誰でも迷わず、可能な限り少ない操作で入力・修正できるUI」にはまだ到達していません。

特に改善余地が大きいのは、レシートのAI確認画面、決済元の推定、スマートフォンでの連続入力、品目の一括変更です。

コード上で確認できた状況をまとめます。

| 領域 | 評価 | 主な理由 |
| -------- | ------ | ----------------------------------- |
| PCでの手入力 | 良好 | Enterによる連続入力、グリッド編集、貼り付け対応 |
| スマホでの手入力 | 改善余地あり | 入力は速いが、共通情報の編集と保存までの導線に無駄 |
| AIレシート確認 | 要改善 | 全品目の確認操作と詳細フォームが重すぎる |
| サジェスト | 改善余地あり | 履歴活用はあるが、商品候補・価格・店名の連携が弱い |
| 一括編集 | 良好だが不足 | 複数選択に対応。ただし操作段階と設定可能な配分に制限 |
| 同時編集 | 一部達成 | 確定済み購入の同期はあるが、共同下書き編集は別問題 |
| 誤操作からの復帰 | おおむね良好 | Undo/Redo・下書き保存・競合表示。ただし修正内容を失う経路あり |

これはソースコードからのレビューです。実機ブラウザで画面を操作したり、タッチ操作の所要時間やスクリーンリーダーの動作を測定した結果ではありません。以下では、コードから確認できる問題と、実機検証が必要な改善仮説を区別します。

すでにある改善点は再タスク化せず、残る具体的な問題に絞ります。

## 1. 最優先で改善するべき問題

### P0-1. AIレシート確認で「確認操作」の意味が一致していない

対象：`receipt-review.tsx` L580–603、`use-import-confirmation.ts` L355–408・L649–696

現在は、認識した各品目に「一致を確認」「未解決にする」ボタンがあります。

未確認の品目はすべて`reviewTargets`に追加され、「前へ」「次へ」で確認を進めるUIにもなっています。

その一方、最終的な`confirm()`は全品目が`CONFIRMED`になっていることを要求していません。

そのため、ユーザーには2通りの行動が生まれます。

- 表示に従って20品目を1つずつ確認し、20回ボタンを押す。
- それらをすべて無視して「帳簿に追加」を押す。

後者でも保存できるのであれば、前者の20回の操作は必須ではありません。さらに、「確認済み」という表示の意味も曖昧です。

#### 改善案

レシート全体を確認する操作と、問題のある品目を修正する操作を分離します。

通常のレシート確認画面は、以下のようにします。

スーパー〇〇

20品目 · 2026/10/14

## ¥4,580

確認が必要な項目が2件あります

ヨーグルト ¥198

税の解釈候補が2通りあります

確認方法の詳細を見る

牛乳

カテゴリ未確定

¥248

ほか18品目

一覧で確認可能

2件の確認後に登録

問題がない場合は、一覧を確認して1回の操作で登録できます。

AI認識結果に問題がなければ、ユーザーによる「帳簿に追加」の1回の確定で十分です。

ただし、AIが高いConfidenceを出しただけで無条件に正しい扱いにはしません。 明細の欠落、合計不一致、重複、根拠領域なしなどを検証し、異常がある部分だけ個別の確認を要求します。

また「未確認」「AI検証済み」「ユーザー確認済み」は異なる状態として扱います。

これが最も操作数を削減できる改善です。

### P0-2. AI確認画面が、最初から詳細編集フォームになっている

対象：`receipt-review.tsx` L370–973

現在の各品目には、品名、AI認識の状態、確認ボタン、カテゴリ、正規化商品、負担割合、登録金額、数量・単価、削除などが配置されています。

いずれも必要な機能ですが、必要な機能を全部最初から見せることと、使いやすいことは別です。

特に20品目あるレシートでは、非常に長い入力フォームになり、ユーザーはすべての項目を視覚的に確認する負担を負います。

さらに、`compactReview`になる条件に`allReceiptItemsReviewed`が含まれているため、すべての品目の確認が済まない限り簡潔な表示へ切り替わりません。

これは、P0-1と組み合わせると悪循環になります。

#### 改善案

通常の品目一覧は、原則として以下だけを表示します。

`商品名　金額　必要な場合だけ注意表示`

品目をタップしたときだけインライン編集を開きます。

「カテゴリ」「正規化商品」「負担割合」は、標準から外れた場合や推定が不確かな場合だけ補助表示します。

数量・印字単価・税率候補などは、さらに詳細表示で操作できるようにします。

PCでは原本画像と一覧を左右に並べ、画像の対応領域をハイライトします。原本領域の双方向選択はすでに実装されているため、その機能を活用できます。

既存の編集機能を削るのではなく、初期表示から隠し、必要なときに最短で開ける構成に変更します。

### P0-3. 決済元を認識できなかった場合に、最初の口座が採用される

対象：`use-import-confirmation.ts` L318–353

`paymentDraftFor()`では、認識した決済情報が存在せず、保存済みの入力もない場合、次の値を設定しています。

```
paymentAccountId: household.accounts[0]?.id ?? ""
```

これは操作数を減らしているように見えますが、正しい決済元だという根拠がありません。

例えば、最初に登録された口座がAの個人口座でも、実際にはBのカードで購入していた可能性があります。

このまま確定すると、後から精算額を修正する必要が生じます。

#### 改善案

決済元の候補を次の順番で判定します。

1. カード末尾番号などによる一意の一致
2. レシートの決済方法・店舗の履歴
3. 同じユーザー・店舗での直近の決済手段
4. 家計内で利用可能な口座が1つだけの場合
5. その他は未確定

複数候補がある場合は、候補を順位付けして表示します。

十分な根拠がある場合は0操作で補完し、曖昧な場合だけ1回の選択を要求するのがよいです。

### P0-4. 金額を修正した際、入力内容が黙って消える可能性がある

対象：`receipt-review.tsx` L667–705

AI確認画面の金額入力では、`onBlur`で入力値を検証しています。

`parseReceiptReviewAmountDraft()`が`null`を返した場合、更新処理は行われませんが、入力用の`receiptAmountDrafts`は削除されます。

つまり、入力途中の不正な値や未完成の値があった場合に、フォーカスを外すと元の金額へ戻る可能性があります。

修正したつもりの値が残らないのは、金融情報を扱うUIでは避けたい挙動です。

#### 改善案

入力値と確定値を別々に保持し、不正な入力はそのまま残します。

その場で「1円以上の整数で入力してください」などのエラーを表示し、訂正するまで確定ボタンを無効化します。

Escapeで変更を破棄、Undoで直前の値に戻ることもできるようにします。

正常な入力であれば、EnterまたはBlurでコミットし、別途「保存」ボタンを要求しない方式が適切です。

### P0-5. 日付しか分からないレシートで、時刻入力が必須

対象：`receipt-review.tsx` L385–407・L945–958、`receipt-confirmation.ts` L73–76

現在、AI取り込みの確定ボタンは`!purchaseTime`の場合に無効になります。また、購入日時生成も時刻がないケースを許容していません。

しかし、ECの注文履歴や領収書には、日付だけで時刻が記載されていないものがあります。

その場合、ユーザーが本来存在しない時刻を手動入力しなければ確定できません。

#### 改善案

`occurredAt`とは別に、日時の精度を持たせます。

- `DATE_TIME`：日時が分かっている
- `DATE_ONLY`：日付だけが分かっている
- `INFERRED`：一部を推定した

日付しか分からない場合は、ユーザーに時刻を入力させずに確定できるようにします。

内部的に検索や並び替えのための代表時刻を持つことは可能ですが、実際の購入時刻であるかのように表示してはいけません。

## 2. 手入力画面の改善

手入力はかなりよくできています。特に次の機能は維持すべきです。

- 品名入力 → Enter → 金額入力 → Enter → 次の品目、という連続入力。
- 購入単位での店名・日時・決済元の共有。
- 複数品目の貼り付け、複数選択、一括変更。
- ローカル下書き保存、送信キュー、Undo/Redo。
- 日本語IMEの変換状態を考慮した確定処理。

ただし、まだ操作数を削減できる部分があります。

### P1-1. スマートフォンで、購入情報の位置と編集方法を改善する

`purchase-create-page.module.css` L103–142、`purchase-create-page.css` L540–670

スマホではCSS Gridで「品目 → 購入詳細 → 購入履歴 → 保存操作」という配置になっています。

品目を先に表示する考え方は適切です。しかし、店名や決済元を変更したい場合、品目一覧より下へ移動する必要があります。

さらに、保存操作の`composer-bottom`は`position: sticky`ですが、DOM上では品目と購入詳細の後に存在します。画面を開いた直後から常時利用できる固定フッターとは異なります。

改善後は、購入情報を画面上部に1行程度で表示する方式がよいです。

スーパー〇〇

今日 · 共用カード

品名

金額

標準負担・カテゴリを自動適用

&#x20;追加

合計 ¥2,426

買い物を保存

モバイル画面の構造例。入力項目が増えても主要操作は近くに保ちます。

店名・日時・決済元を変更したい場合だけ、上部をタップしてインライン展開します。

保存操作はスクロール位置とソフトウェアキーボードに応じて表示するコンパクトな固定アクションとし、入力内容を隠さないようにします。

### P1-2. 商品名サジェストは、価格入力まで短縮できる

`edit-purchase-items.tsx` L404–441、`product-suggestions.ts` L29–77

現状は、過去の商品名や商品マスタから候補を表示します。しかし、候補を選んだ後は基本的に金額欄へ移るだけです。

同じ商品を繰り返し購入する場合、商品名だけでなく価格も再利用できます。

ただし、前回価格を無条件に確定させるのは危険です。

おすすめは、候補を選んだ際に、直近価格を金額欄の近くに表示する方式です。

例えば、「ヨーグルト」を選んだときに「前回 ¥198」をワンタップで適用できるようにします。表示する価格には、店舗、容量、購入日などの根拠も持たせます。

金額が変わっていれば通常どおり入力できます。

これなら、価格が同じ買い物では数字を入力する操作がなくなります。

### P1-3. 一括負担変更で自由な比率を指定できない

`edit-purchase-items.tsx` L638–648・L705–727

手入力画面の一括負担変更では、現在の選択肢が実質的に次のものに限定されています。

- 標準配分に戻す
- 指定したプールが100%負担

しかし、当初の要件ではA:B=3:2などの任意配分を頻繁に利用します。

各品目を個別に編集すれば変更できても、複数品目へまとめて設定できないのは不便です。

一括編集でも、個別品目と同じ負担割合エディタを使えるようにするべきです。

さらに「この選択を次からのデフォルトにする」機能も、誤操作を防ぐ確認を伴って提供するとよいです。

### P1-4. 一括編集の確定操作が多い

現在の新規購入画面では、「品目を選択 → カテゴリを選択 → カテゴリ変更ボタンを押す」という操作です。

通常のカテゴリや負担割合変更は即時反映し、最後の確定ボタンを省略できます。Undoがあるので誤選択からの復帰も可能です。

ただし、締め済み帳簿への訂正など、会計上の影響が大きい変更は明示的に確認します。

### P1-5. 店舗と決済元の予測が端末内の履歴に依存している

`purchase-defaults.ts` L39–113

現在は`localStorage`に、以前の店舗とその店舗で使用した決済元を保存しています。

同じブラウザを使い続ける場合には効果的ですが、PCとスマホを切り替えた場合、購入の入力に使える履歴の一部が共有されません。

店舗別の決済履歴をバックエンドで管理すれば、スマホでもPCでも適切な初期値を選択できます。

また、店名の表記揺れを考慮した正規化も必要です。

「イオン」「イオン〇〇店」「AEON」が別店舗として扱われると、せっかくの履歴が活用されません。

保存直後に前回の店舗名を入力欄へ残す現在の設計も、連続して同じ店を入力するときには便利ですが、異なる店舗の買い物を続けて入力するときには誤登録の原因になり得ます。明示的な「前回と同じ店」候補と、店舗名を未選択にした新規入力とを使い分けたいです。

### P2-1. サジェストの履歴が直近80購入に依存している

`purchase-create-page.tsx` L227–241

手入力の過去履歴は80購入を取得し、その中から商品候補などを生成しています。

利用開始直後は問題になりませんが、購入履歴が何千件にもなると、頻繁に購入する商品が直近80購入に存在しないこともあります。

商品サジェストは、購入履歴の取得件数に依存せず、商品マスタと購入統計に基づいたサーバー側の候補検索へ寄せるべきです。

また、候補のランキングには、単なる一致度だけでなく店舗・購入回数・直近購入日・ユーザーの確定実績を反映するとよいです。

## 3. AI取り込みの操作数をさらに減らす

### P1-6. カメラで連続撮影する導線が弱い

`camera-capture.tsx` L205–240、`imports-page.tsx` L415–461

現在、カメラで撮影した画像は確認画面を経由して取り込みに追加され、アップロードされます。

しかし、1枚追加すると撮影用のダイアログが閉じます。

複数枚のレシートをまとめて撮影したい場合、毎回カメラを開き直す必要があります。

改善案は、撮影後に「次のレシートを撮影」を続けられるようにすることです。

アップロードと解析は裏側で並行して開始し、複数枚を撮影した後に確認待ち一覧へ移動できます。

なお、同じ長いレシートを分割して撮影する場合と、別々のレシートを連続撮影する場合は区別します。前者では複数画像を1つの原本グループとして扱う必要があります。

### P1-7. レシートの品目修正に金額訂正理由が要求されすぎる

`use-import-confirmation.ts` L649–680

`requiresOverrideReason`では、品目構成を変更しただけでも訂正理由が要求される経路があります。

例えば、AIが誤って1行として認識した2商品を手動で分割して、合計金額が変わらなかった場合でも、訂正理由の選択が必要になる可能性があります。

本当に理由が必要なのは、監査上の説明が必要な操作です。

品目の編集内容自体が変更の根拠になる場合は、追加の理由入力を省略するべきです。

一方、原本合計と帳簿合計が一致しない状態で強制確定する場合は、理由を要求するのが適切です。

### P1-8. 取り込みと手入力の切り替えが遠い

`home-page.tsx`、`imports-page.tsx`、`purchase-create-page.tsx`

現在は「買い物を追加」と「レシートを取り込む」が別画面として設計されています。

もちろん内部処理は異なりますが、ユーザーから見るとどちらも「買ったものを登録する」という1つの目的です。

そのため、アプリの主要操作を「支出を追加」に統合し、最初の操作で以下の方法を選べるようにするとよいです。

`レシート撮影 / 画像から入力 / 手入力 / 履歴からコピー`

ただし、毎回選択ダイアログを強制表示しては逆効果です。

ホームの主ボタンは前回使った方法を直接起動し、隣の小さなメニューからほかの方法を選べる方式にします。

スマホではカメラへの直接アクセスも残します。

## 4. 帳簿編集・同時編集の改善

### P1-9. 品目編集で、編集モードと保存操作が必要

`ledger-page.tsx` L360–430、`use-ledger-purchase-editor.ts` L299–429

現在、品目単位の編集では「品目を編集」で編集モードに入り、変更後に「変更を保存」を押します。

金融情報なので、保存時の競合検出や確認は重要です。しかし、日常的な品名・カテゴリ修正まで毎回保存ボタンを必要とするのは操作数を増やします。

ここは、通常変更を自動保存し、Undoで取り消せる方式を検討する価値があります。

ただし、確定済みの会計台帳を更新する以上、ローカル表示だけ保存済みに見せるのは避けなければなりません。

推奨する方式は、入力値を即時反映し、Blurや短いアイドル時間で保存するものです。保存中・保存失敗・競合は明確に表示し、競合時には変更内容を失わずに解決できるようにします。

締め後の訂正や返金は従来どおり明示確定とするべきです。

### P1-10. 複数人が同じ「未確定の買い物」を共同編集できない

`use-purchase-draft.ts`、`purchase-storage.ts` L324–340

現在の新規購入の下書きは、ユーザーと家庭をキーにしてIndexedDBへ保存されています。

一方、確定済みの購入記録はGraphQL Subscriptionによって更新通知を受け、競合検出にも対応しています。

つまり、複数人がそれぞれ別の買い物を追加したり、確定済みの購入を編集したりするための仕組みは存在します。

しかし、同じ未確定の買い物をスマホとPC、またはAさんとBさんで共同編集するための共有下書きモデルは確認できません。

当初の「複数人で同時編集」を同じ買い物の編集中にも求めるなら、ここは未達成です。

改善するなら、下書きをサーバー側でも共有し、品目単位・フィールド単位の更新イベントを配信します。

金額・負担配分などの会計データは安易にCRDTでマージせず、サーバー側のリビジョン管理で確定させる方式がよいです。

ローカルのIndexedDBはオフライン編集のために残します。

## 5. さらに小さな改善点

| 優先度 | 問題 | 改善方法 |
| --- | ------------------------------- | ------------------------------------ |
| P2 | 購入履歴のコピーで前回価格がそのまま入る | 保存前に前回価格との差分・購入日を自然に確認できるようにする |
| P2 | 商品候補が確認済み・履歴・商品マスタで多数表示され得る | 最も可能性の高い候補を少数表示し、「もっと見る」で展開 |
| P2 | 新規購入画面のカテゴリ選択が常時表示 | 通常は自動適用し、未分類または変更時のみ目立たせる |
| P2 | 帳簿検索に単純な月範囲入力が常時ある | 「今月」「先月」「過去3か月」などの頻出プリセットを優先 |
| P2 | AI確認の品名入力欄がすべて`aria-label="品名"` | 商品名や行番号を含む識別可能なラベルへ変更 |
| P2 | 帳簿検索のEnter処理でIME変換状態を確認していない | `isComposing`を考慮し日本語変換確定を検索確定として扱わない |
| P2 | 設定した負担割合の初期値が、品目一覧では簡単な名称表示だけ | 比率と実際の各プールの負担をワンタップで確認できるようにする |
| P2 | 入力中に表示されるカテゴリ・決済元が多数になる可能性 | 最近の選択・頻度・検索を優先し、全候補は必要時だけ表示 |

これらは大規模な再設計よりも、入力中の細かな摩擦を減らす改善です。

## 6. 改善の優先順位

私は次の順番で修正するのがよいと思います。

| 順位 | 改善 | 期待効果 |
| -- | ----------------------- | ------------------ |
| 1 | AI確認を「全品目操作」から「例外中心」に変更 | 1レシート当たりの確認操作を大幅削減 |
| 2 | AI確認画面の詳細項目を段階表示 | スクロール・視線移動を大幅削減 |
| 3 | 決済元の正確な推定 | 誤登録と後からの修正を削減 |
| 4 | 金額修正で入力内容を失わない | 修正のやり直しを防止 |
| 5 | 日付のみでの取引登録 | 不要な時刻入力を廃止 |
| 6 | スマホの入力画面を再整理 | 画面移動・スクロールを削減 |
| 7 | 商品候補から価格まで再利用 | 頻出商品の入力を高速化 |
| 8 | 任意比率を含む一括編集 | 複数品目の修正を短縮 |
| 9 | 連続撮影・取り込み導線の統合 | 複数レシート登録の操作を削減 |
| 10 | 通常の帳簿編集を低摩擦化 | 日常のカテゴリ・名称修正を高速化 |

## 7. UIの完成度をどう検証するべきか

今後は、コード上の設計だけでなく、代表的なユーザー操作を自動テストとして固定するのがよいです。

例えば以下を、スマホとPCの両方でPlaywrightにより検証します。

| シナリオ | 目標 |
| -------------- | ------------------- |
| 1品目を手入力 | 品名・金額以外の入力は通常不要 |
| 10品目を連続入力 | 途中で不要な画面遷移なし |
| 過去に買った商品を再入力 | 候補から品名を選び、価格も簡単に再利用 |
| 10品目中3品目の負担変更 | 複数選択して1回の配分操作 |
| 正常なレシート20品目 | 個別の確認ボタン20回は不要 |
| AIが2品目間違えたレシート | 2箇所の修正と全体の確認だけ |
| 2枚のレシートを撮影 | カメラを毎回開き直さない |
| 1品目のカテゴリを修正 | 編集画面への移動なし |
| 金額の入力を途中で中断 | 入力内容が保持される |
| 2人が同じ取引を修正 | 内容が失われず競合を解決できる |

ここでは、クリック数だけでなく、入力時間、キーボード切替回数、スクロール距離、誤操作数、取り消し回数も測定します。

単に「クリックが少ない」だけでなく、利用者が判断しなければならない回数を減らすことも評価すべきです。

例えばAIが自動的に20件の商品名を入力していても、20件すべてを人間が詳しく確認しなければならないなら、入力補助の価値は大幅に下がります。

## 最終評価

Horseの現在の実装は、入力フォームや履歴編集に必要な仕組みがかなり揃っており、単純なCRUD家計簿よりはるかに高度です。

特に、連続入力、コピー、下書き保存、一括編集、原本と帳簿の対応、競合解決は、すでに有用な基盤ができています。

しかし、最も操作数を減らせる余地があるのは、さらに機能を増やすことではありません。

既存機能を、普段は意識せず使えるようにすることです。

AIが正しく認識したら個別操作は不要。カテゴリが推定できたら選択不要。決済元が一意に分かれば選択不要。履歴に同じ商品があれば、品名と価格を簡単に再利用。誤った部分だけを短い操作で修正する。

こうした考え方で、特にAI確認画面とスマホの購入入力画面を再設計することが、当初の「入力の手間が限りなく少ない家計簿」に近づくための最も重要な改善だと考えます。

なお、実際の画面の視覚的な完成度、タップしやすさ、フォーカス挙動については、コードレビューだけでは完全に評価できません。最終的には実機操作・画面キャプチャ・E2Eテストを併せて検証する必要があります。
