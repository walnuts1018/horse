# Horse UI/UX追加レビュー — 既存指摘を除外

対象：[walnuts1018/horse](https://github.com/walnuts1018/horse) の `main` ブランチ

今回は、`docs/reviews/README.md`、`code.md`、`design.md`、`gemini.md`、`lack.md`、`ux.md` を確認し、既存レビューに載っていない具体的な問題だけを対象にしています。

とくに、新規購入・品目の連続入力・支払元の編集・レシート取り込みについて、実装をたどりました。以下は新たに確認できた問題です。なお、これはソースコードレビューであり、ブラウザ実機で再現した結果ではありません。

## 1. 優先度の高い改善

### 1-3. レシートの切り抜きが原本を置き換えてしまう

P1 · 証拠情報の欠落

対象：[camera-capture.tsx](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/ui/camera-capture.tsx#L144-L170)

撮影時に切り抜き範囲を指定すると、Canvasで切り抜いた画像から新しい`File`を生成し、それを`onAdd(file)`へ渡しています。

そのため、少なくともこのアップロード経路では、元の画像ではなく切り抜き後の画像だけが送信されます。回転操作についても、元の画像を処理結果で置き換えています。

後から証拠を再検証したいアプリとしては、原本が失われる設計は避けるべきです。

改善案： 撮影原本と解析用画像を分離します。

原本のバイト列は変更せずにSeaweedFSへ保存し、補正・回転・切り抜きは変換パラメータとして記録します。AIには必要に応じて補正画像を送ります。

これにより、利用者は気軽に切り抜きでき、将来別のAIモデルで再解析するときにも原本を利用できます。

### 1-8. レシートの購入日を修正すると、認識済みの購入時刻が失われる

P1 — 意図しない情報変更

対象：[imports.ts:59–73](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/model/imports.ts#L59-L73)

`receiptOccurredAt()`では、購入日だけを変更しても、抽出済みの購入時刻を維持します。

例えばAIが「10月12日 18:32」と認識し、日付だけを「10月13日」に修正すると、保存される日時は「10月13日 18:32」になります。

ユーザーは時刻を修正したつもりがないのに、時刻が変更されてしまいます。

対応状況： 認識済みの時刻は日付変更後も維持します。時刻が不明な場合は現在も12:00を補完値として使うため、時刻不明の表現と保存方法は未解決です。

日時全体を変更したい場合だけ、時刻編集も開けるようにします。

### 1-10. 税計算候補が、何を意味する候補なのか理解しにくい

P1 — 確認に必要な思考・操作を減らす

対象：[receipt-review.tsx:390–421](https://github.com/walnuts1018/horse/blob/main/web/src/pages/imports/ui/receipt-review.tsx#L390-L421)

税計算候補には、候補ID、合計一致の状態、問題点、計算合計が表示されます。

しかし、候補の違いが税込・税抜なのか、税率の違いなのか、値引きの解釈なのかが一覧から分かりません。

ユーザーは候補を選び直して金額の変化を見比べる必要があります。

改善方法： 候補を「全品税込」「一部税抜・軽減税率8%」「値引きを商品別に配賦」など、人間が意味を理解できる名称で表示します。

候補間で金額が異なる品目だけを強調し、差異のある箇所へ移動できるようにします。

バックエンド側の計算候補にも、説明可能な税率・税区分・値引き適用先などの構造を追加するのが適切です。

## 3. 追加で改善したい入力UIの設計

既存レビューで提案済みの項目を再掲するのではなく、今回見つけた問題を解消するための具体的な状態設計です。

### 3.1 決済額には「自動残額」という概念を設ける

現在の決済入力には`autoTotal`がありますが、基本的に1口座の場合に限られています。

これを複数口座にも拡張し、最後の1口座が残額を自動的に引き受ける設計を推奨します。

決済内訳

商品合計 ¥2,980

クレジットカード

¥1,980

自動残額

現金

¥1,000

手動指定

差額

¥0

この形式であれば、決済元が2つでも金額入力は1回で済みます。

さらに、手動金額の変更で残額がマイナスになった場合は、その場で分かるようにします。

既存の単一口座向け`autoTotal`を拡張するのが自然で、新しい複雑な操作体系を追加する必要はありません。

### 3.2 AI確認では「解析結果」と「編集中の値」を分ける

残っている確認状態の未保存、時刻不明の扱い、AI再解析結果との統合は、AIの解析結果とユーザーの編集中データの責務を分ける必要があります。

次のように扱うのが適切です。

```
原本
  ↓
AI解析結果（不変）
  ↓
編集セッション（自動保存）
  ├─ 解析結果の採用
  ├─ 人間による修正
  ├─ 税計算候補の選択
  └─ 決済元・負担先の確定
  ↓
帳簿登録のプレビュー
  ↓
確定
```

表示する金額は常に編集セッションの値を参照し、最終Mutationも同じ状態から生成します。

この構成なら、画面の表示値と確定Mutationの値を同じ編集セッションから生成できます。

また、ユーザーが手動で修正した項目をAIが後から再解析しても、その修正を勝手に上書きしないようにできます。

## 総評

今回の追加レビューでは、見た目の改善というよりも、ユーザーが入力・修正した内容と、アプリが保持・保存する状態のズレが目立ちました。

特に問題なのは次の3点です。

第一に、入力の途中状態が十分に保護されていないこと。 新規購入の下書き保存は整備されていますが、AI確認や既存帳簿編集には同等の保護がありません。

第二に、入力値の自動計算が場面ごとに一貫していないこと。 新規購入では単一決済の合計自動反映ができるのに、分割決済やAI確認ではその考え方が統一されていません。

第三に、ユーザーに提示する値と、最終的な保存値が異なる可能性があること。 とくに税計算候補に関する問題は、家計簿の信頼性に直接影響するので優先して修正すべきです。

最初の要件である「手入力を極限まで簡単にする」を実現するには、単にタップ数を減らすだけでなく、入力をやり直す必要が生じないこと、勝手に値が変わらないこと、ユーザーが一度決めたことを再度決めさせないことが重要です。

その観点で、今回の新規指摘はかなり実益のある改善対象だと考えます。
